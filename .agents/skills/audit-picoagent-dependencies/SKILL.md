# PicoAgentの外部依存を監査する

## 対象を決める

1. 引数を `all`、`packages`、`apps`、または個別カテゴリとして扱う。省略時は `all` にする。
2. `packages` はCargo、npm、Python、その他のパッケージマネージャー管理物を対象にする。
3. `apps` は同梱・管理導入・開発用取得する実行ファイル、モデル、Webランタイム、外部CLIを対象にする。
4. 個別指定では `cargo`、`web`、`python`、`aivis`、`whisper`、`engine`、`models`、`live2d`、`office`、`tools`を受け付ける。

## 棚卸しする

1. `python .agents/skills/audit-picoagent-dependencies/scripts/inventory.py <対象>` を実行する。
2. 表示されたマニフェスト、ロック、固定版、取得URL、ハッシュ、`latest`追従、ローカル実体をすべて確認する。
3. `rg`で `VERSION`、`targetVersion`、`releases/download`、`releases/latest`、`resolve/main`、`sha256`、`integrity`、CDN URLを再検索し、棚卸しスクリプトの漏れを点検する。
4. Git管理外の `src-tauri/resources/bundled/` 実体も、実行ファイルの版表示または同梱マーカーで確認する。
5. 大容量取得の呼び出し元を逆引きし、起動、通常ビルド、引数省略、インストール後処理が任意モデル・ランタイム・SDKを暗黙取得していないか確認する。
6. OS、CPUアーキテクチャ、GPU種別、必要能力を取得前に判定しているか確認する。CUDA版はCUDA対応NVIDIA GPUだけ、ROCm版は各社公式対応表に載るAMD GPUだけを対象とし、非対応GPUとGPUなし環境では取得しない。1つの機能へ複数バックエンドの大容量ランタイムを同時導入していないか、導入済みマニフェストへGPU種別とバックエンドを記録して不一致の再利用を止めているかも確認する。CPU版を選ぶのは対象機能がCPU実行を正式対応する場合だけにする。
7. PicoAgent管理下に旧版、退避、staging、`.part`、`.incoming`、`*-old-*`、成功済み処理の再開キャッシュが残っていないか確認する。新版検証後の旧版削除と、失敗後の次回成功時回収を取得処理ごとに追う。

## 公式最新版と照合する

1. GitHub Releases、crates.io、PyPI、npm、各公式配布元など一次情報だけを使う。
2. 公式LTSまたは長期保守安定版がある場合はLTSを優先し、無い場合は安定版latestを採用対象とする。nightly、preview、RCは明示指示がない限り採用しない。互換性、対象OS資産、ライセンス、再現可能なハッシュ固定に具体的な問題がある場合だけ他の旧版を維持する。
3. 「最新版の版」と「PicoAgentが実際に取得・配布する版」を分けて記録する。旧版を維持する場合は固定理由と確認日を記録する。
4. `latest`追従も合格扱いにせず、現在解決される版、アセット名、対象OS、サイズまたはdigestを確認する。
5. URLが生きているだけで合格にせず、期待するアセットと実体が一致することを確認する。
6. LLMモデルだけはLTSを選ばず、公式の最新安定版を常に採用する。プリセット名、リビジョン、量子化方式、URL、サイズ、SHA-256を実体と照合する。

## 更新する

1. パッケージ更新とアプリ更新はユーザー指定に応じて同じPRまたは目的別PRへ分ける。
2. Cargo更新では各ロックを更新し、直接依存のメジャー更新も確認する。`Cargo.toml`または`Cargo.lock`を変えたら各ロックへ`cargo audit --file`を実行する。
3. アプリ更新では固定版、取得URL、アセット選択、ハッシュ検証、版マーカー、対応OSを同期する。
4. 条件別アセットでは、非対応環境がダウンロード開始前に停止または対象を除外する実装と回帰テストを追加する。単に取得後の起動で失敗させない。
5. 新版の検証成功後に旧版と一時物を削除し、正常終了後の管理領域に不要物が0件であることを確認する。失敗時の復旧物を残す場合は次回成功時の削除経路も同じ実装に入れる。
6. Git管理外の同梱実体を配布する場合は、最終ビルド直前に正規取得入口から再取得し、実体の版を再確認する。
7. 現行情報をREADMEとSPECへ反映し、監査結果をPR本文へ書く。未完了・条件待ちだけを`docs/TASKS.md`へ反映し、未マージ作業の再開情報が変わる場合だけHANDOFFを更新する。

## 任意の画像・動画モデルを実機で導入する

1. `docs/models.md`と`character-maker/sidecar/media/model_catalog.py`を照合する。利用者へ取得量、GPU・RAM条件、商用条件、低メモリ化の速度・画質差を示し、明示承認の前にはモデルを取得しない。
2. 新NVFP4経路では`setup_models.py --preflight-only`で本人の利用条件確認版、実GPU、空き容量、全資産へのアクセスを先に検査する。認証は本人の`hf auth login`を使い、トークンを会話・ログ・引数へ出さない。
3. `setup_runtime.py`を正規入口にして、共通Python本体を再利用する独立した`bundled/media-runtime`を作る。既存キャラ作成venvを書き換えず、旧モデル77GBの導入を代用しない。新Comfyで高速CUDAバックエンドが有効なことも確認する。
4. `setup_models.py`から承認済みモデルだけを取得し、固定サイズ・SHA-256・利用条件文書・導入マーカーを検証する。転送停止は再開位置と実プロセスを確認して復旧し、取得中と誤報告しない。成功後はその処理が所有する再開用ファイルだけを回収する。
5. `generate.py --lowvram`の小さい固定条件で生成し、静的テスト、実ノード登録、実生成、画質、速度を別々に報告する。成功・失敗の双方で専用Comfyと子プロセスを回収する。未確認の機種、品質経路、クリーン導入は`docs/TASKS.md`へ残す。

## 毎月点検する

1. CodexのScheduled taskでは毎月1日に、このリポジトリを分離worktreeで開き、`$audit-picoagent-dependencies all`を実行するよう登録する。
2. 更新があれば目的別ブランチで修正、検証、PR、squash mergeまで行う。更新が無ければ変更を作らず、点検結果だけを報告する。
3. Scheduled taskの実行にはCodexデスクトップアプリが起動中で、PCが稼働している必要がある。CLIだけで登録済みと主張せず、Scheduled画面に登録が見えることを確認する。

## 検証する

1. 変更した各マニフェストへ`cargo check`、対象テスト、必要な`cargo clippy -- -D warnings`を実行する。
2. 取得処理はURL組立、OS別アセット選択、ハッシュ拒否、版比較のテストを通す。
3. 配布物を作る場合は、インストーラ内へ入った実体の版と、公開後に再取得した配布物のサイズ・SHA-256を照合する。
4. PR本文へ対象、現行版、上流版、更新・見送り理由、監査結果、未確認事項を書く。後続作業が必要な項目は`docs/TASKS.md`へ着手条件付きで残す。
5. 正常終了後に管理領域の旧版・一時物・完了済みキャッシュが0件であることを検索結果で確認する。
6. 完了報告では「packages」「apps」を分け、各カテゴリの採用版と保留を明示する。

## 停止条件

- 一次情報から最新版または配布条件を確認できない。
- 更新後に対象OSのアセットが存在しない。
- ハッシュや署名を検証していた経路が弱くなる。
- ライセンスまたは再配布条件が不明になる。
- 実体の版を確認できないまま公開ビルドへ進もうとしている。
