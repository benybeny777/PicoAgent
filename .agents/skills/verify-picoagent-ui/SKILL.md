# PicoAgent実画面QA

## 最初に読む

1. `AGENTS.md` と `HANDOFF.md` を読む。
2. `tools/screenshots/README.md` を最後まで読む。
3. 最新のモニター利用指示を確認する。可視GUIを使わずに済む検査はヘッドレスで行う。
4. `git status --short` で既存変更を確認し、巻き戻さない。

## 調査する

- `ui/`だけでなく、`cargo xtask build-ui`後の`ui-dist/`とTauri commandの実行経路を追う。
- CSS、DOM、配信アセット、キャッシュ版、ウィンドウ寸法を別々に測り、見た目だけから原因を決めない。
- MMDは製品CSP付きWebViewでPMXと全テクスチャを読む。確認用HTTP画面だけの成功では足りない。キャラ読込失敗時に代替キャラ・音声・背景が別々のIDにならないこと、失敗理由が音声準備や起動完了で消えないことも確認する。
- 初回も起動準備中は進捗だけを見せ、選択キャラ・背景・使用するAIと記憶検索モデル・必要な音声・保存寸法が揃ってから通常画面が表示されることを確認する。失敗時に別キャラを出さず、キャラなしの診断へ進むことを検査する。可視確認は完成状態だけを指定モニターへ出す。
- 設定反映後の再初期化でも窓が戻ることを確認する。準備中に呼び出しホットキーまたは多重起動で待ち画面が出ること、起動が止まった場合に案内ページへ切り替わることを、初回起動と再初期化の両方で検査する。
- キャラ画像は正本`characters/`と配信コピー`ui/assets/characters/`の寸法・内容版・参照世代を比較する。
- レイヤー問題は背景、画面内ディスプレイ、キャラ、字幕、操作UIの積層コンテキストまで確認する。

## エラー診断の順序を守る

- 画面のエラー文は診断結果ではなく、コードが選んだ表示候補として扱う。`未導入`、`見つからない`、`停止中`と表示されても、回避策や再インストールを提案する前に、対象実体、管理マニフェスト、実行中プロセス、設定値、探索候補の順序を照合する。
- 元の依頼を早く再開するためにエラーを迂回しない。原因修正、依存処理の停止、診断画面へ到達できる復旧経路の順で扱い、表示を消すだけの変更を採用しない。
- 優先候補とフォールバックを変更した場合は、両方がある通常条件だけでなく「高優先候補だけがある」「フォールバックだけがある」「候補が0件」のテストを追加する。高優先候補の解決前にフォールバックの存在を必須にする実装を許可しない。
- ある工程がエラー状態を通常値で返す場合は、直後の依存工程がその値を停止条件として検査するテストを追加する。後続表示が元のエラーを上書きしないことも確認する。

## 検証する

- まず`tools/screenshots/ui-check.mjs`で3形式の画素・操作部品の完全包含（窓内・親のoverflow・前面要素の遮蔽）・右クリック文脈・矩形保存を検査する。見た目の修正では`UI_CHECK_CHARACTERS=all`で全キャラを対象にする。必要なら`SHOOT_CHARACTER_MATRIX=1`などの旧撮影ツールで実機の追加確認を行う。
- 代表レイアウトだけで済ませず、変更に関係する現行3形式を確認する。
- スクリーンショットを実際に開き、キャラの鮮明さ、切れ、左右位置、前後関係、操作部品を目視する。
- 一時画像・結果は`temp/`だけへ置き、成果物のREADME WebPだけを`docs/images/`へ出す。

## 実Tauri WebViewを直接検査する

- ブラウザ配信では足りないMMD描画・CSP・assetプロトコルは、WebView2のリモートデバッグで実アプリを検査する。`tauri.conf.json`の`additionalBrowserArgs`が環境変数`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`を上書きするため、環境変数だけではポートが開かない。検査中だけ`additionalBrowserArgs`へ` --remote-debugging-port=9222`を足して`cargo xtask dev`で起動し（コミットしない。終了後に必ず戻す）、`http://127.0.0.1:9222/json/list`のページターゲットへ`Runtime.evaluate`を送る。Playwrightからは`tools/screenshots/native-inspect.mjs`の`withNativePage`を使い、接続時に`noDefaults: true`を必ず指定する。接続後に`emulateMedia`を解除する旧手順は、解除前に白いフレームが出るため使用しない。テーマ・省モーション・フォーカスを検査側の既定で上書きしない。状態取得・撮影の入口は`tools/screenshots/README.md`を参照する。`ui/app/main.js`はES Moduleなので、旧`renderer.js`のスクリプトスコープ変数を直接評価する手順は使えない。DOMと公開された契約から状態を確認する。
- 検査のために選択キャラ・表示形式を設定から切り替えてよい（利用者判断）。切り替える前の値を控え、検査の最後に必ず元へ戻す。キャラの変更は再起動で反映されるため、アプリを止めた後に戻した場合も設定値を確認する。
- 利用者の登録データを書き換えない。検証用の表情やモーフ名は、同じPMXを隠しcanvas（`position:fixed;left:-10000px`）へ読み直した第2のコントローラへ渡し、成功・失敗のどちらでも`dispose()`とcanvas削除を通す。
- 待ちは`setTimeout`で刻む。`requestAnimationFrame`はウィンドウが背面だと絞られて戻らず、評価そのものが返らなくなる。
- 画像はページ内で切り出し・縮小してからJPEGで運ぶ。等倍PNG（1枚300KB超）を`returnByValue`で返すと受信が返らない。canvasの実バッファは画素密度で拡大されるため、切り出し座標は`canvas.width`基準の比率で指定する。
- 補間やまばたきのように途中経過を見る対象は、`capturePreview()`（目標へ一度で到達する）ではなく描画ループのバッファを連続で取り、目領域の暗部率のような数値と画像の両方で確認する。
- 検査後は`cargo xtask stop`でアプリと付随プロセスを回収し、一時スクリプトと画像は`temp/`だけへ置く。

## キャラ作成のGPU工程を検証する

- 導入済みの管理PythonとComfyUI、モデル実体を確認してから、docs/DEVELOPMENT.mdのverify_pipeline入口を使う。検証のための追加取得や製品への登録を混ぜない。
- 出力はtemp配下の未使用フォルダへ限定し、入力原画と既存成果物を保持する。
- report.json、工程ログ、生成画像を照合し、既知原画の回帰検査と未知原画の品質評価を区別する。4工程成功だけで生成品質やネイティブUIまで合格にしない。
- Windows操作APIがアクセス拒否の場合はセッションを終了し、実画面操作を未確認として記録する。ヘッドレス画像をネイティブ操作の証拠として扱わない。

## 完了条件

原因、修正、機械検査、目視結果をPR本文へ記録する。仕様変更は`SPEC.md`、利用手順変更は`README.md`へ同期し、未確認項目だけを`docs/TASKS.md`へ残す。`git diff --check`を通してコミット・pushする。
