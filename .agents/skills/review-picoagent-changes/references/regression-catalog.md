# 過去のデグレ台帳

PicoAgentで実際に起きた退行・再発を、レビュー観点ごとにまとめる。各節の「見る」は差分を読むときの質問、「固定済み」は既に機械検査がある範囲で、そこは手で再検査せず、検査の穴だけを見る。参照はコミットハッシュまたはPR番号で、詳細は `git show <hash>` と旧 `docs/REVIEW-LOG.md`（`git show 749b329^:docs/REVIEW-LOG.md`）にある。

新しい型のデグレを見つけたら、レビューと同じPRでこの台帳の該当節へ1行追記する。既存の型の再発なら、その行へ参照を足す。

| 中断復旧で退避データを誤って削除した | #339 |
| 記憶一覧の応答に `items` が無いだけで「0件」と描画した（保存データは残っているのに誤表示） | 2026-08-19 再点検 |
| 並列ツール呼び出しで同じ一覧を書き戻し合い、追加分が消えた | `30deae3` |
| 2つ目のインスタンスが古いスナップショットで設定・記憶を上書きしうる | 単一起動導入前の保留 |
| モデル取得の一時ファイル名を取得ごとに固有にした結果、強制終了で残った数GBの途中ファイルを次の取得が上書きも回収もしなくなった | #415 で混入、直近マージのレビューで修正 |

見る:
- 読めない・壊れている・形が違う入力を空で続けたあと、その空を保存へ流す経路が無いか。JSの `?? []` / `|| {}` / `JSON.parse` の `catch` も同じ。
- 削除・掃除・移行の対象集合が、本当に消してよい物だけに絞られているか。利用者の他プリセット、共有キャッシュ、外部配置を含めていないか。
- 一時ファイルの名前を変えたとき、強制終了で残った旧名・別名の途中ファイルを次の成功時に回収するか（AGENTS「依存と同梱物の取得」）。
- 応答の形が想定外のとき、表示を空へ置き換えず現状を保つか。
- 読む→直す→書き戻すが `store::lock_state` の中か。

固定済み: `store::guard`（直接 `fs::write`、退避もエラーも無い空置換、ロック無しの書き戻し）。

見る:
- `continue` / 早期 `return` / `.ok()` / `unwrap_or_default()` / 空 `catch` で、利用者が「できている」と思う機能を黙って諦めていないか。

- 裏で繰り返す機能の失敗が `notifyBackgroundFailure` で原因ごとに1度画面へ出て、復旧で解除されるか。
- エラー文が実在する操作導線を示し、内部用語・`undefined`・秘密値を含まないか。
- 失敗時に別キャラ・別の声・別モデル・別描画方式・別の検索方式・既定値へ切り替えていないか。許可は `AGENTS.md` の根拠（利用者決定）があるものだけ。
- エラーの種類（再試行可否・認証失敗など）を文字列の部分一致で判定していないか。状態コードや型で判定する。
- 数値・列挙の設定を、保存時に範囲で検証しているか。実行時の `parse().unwrap_or(既定)` で黙って読み替えていないか。
- 取得できない値を作り値（`Ok(0)`・`u64::MAX`・空文字）で返して、後段の検査を必ず失敗・必ず成功させていないか。取得できないならエラーにする。
- 記録ファイルが「無い」と「読めない・壊れている」を同じ値（`None`）へまとめ、検査（GPU一致・版の照合など）を素通しさせていないか。
- 候補を順に試して最初に成功したものを使う処理（画像・展開ツール・実行ファイル）が無いか。使うものは条件から1つに決め、失敗は理由つきで出す。
- 失敗の印と状態の単位（キャラ・ファイル・機能）が一致しているか。別の単位の成功で解除していないか。復旧の無い出来事を、復旧を待つ失敗の仕組みへ載せていないか。

固定済み: `tools/tests/background-failure-contract.mjs`、`error-message-contract.mjs`。

## D4 外部プロセス・リソース回収

- 出力回収を順番に待ち、先の読取失敗で後の読取タスクを切り離していた。両系統の所有者が、失敗・中断・終了確認エラーを含む全経路で中断する（設定・天気の追加レビュー）。
