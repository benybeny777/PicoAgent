# PicoAgentの変更をレビューする

`AGENTS.md` のとおり、利用者が「読み取り専用」「編集禁止」と明示していない限り、レビューは修正・テスト・PRまでの依頼として扱う。指摘を並べて終わりにしない。

## 対象を決める

1. 依頼から対象を1つに決める。
   - PR番号 → そのPRの差分（`origin/<base>...<head>`）。
   - ブランチ・コミット範囲 → その範囲。
   - 「直近マージ」「最近の変更」 → 前回のレビューPR以降の `main`。`git log --format='%h %s' origin/main | grep -m1 'レビュー指摘'` で起点を探し、そこから `origin/main` まで。見つからなければ直近10コミット。
   - 未コミット変更 → `origin/main` との差分と作業ツリー。
2. `git fetch origin main` してから `git log --oneline <範囲>` と `git diff --stat <範囲>` で規模を掴む。画像・`character.json`・生成物は差分を読まず、参照と寸法だけを確認する。
3. 既に未コミット変更がある場合は利用者または別エージェントの作業として扱い、巻き戻さない。
4. レビューは作業中のエージェント自身で完結させる。CodexとClaudeは互いを起動せず、相互レビューは利用者が担当と範囲を明示した場合だけ行う（`AGENTS.md`）。

## 準備する

1. `AGENTS.md`、`HANDOFF.md` を読む。変更対象に応じて担当文書（`SPEC.md`、`docs/SETTINGS.md`、`docs/UI-CONTRACT.md`、`docs/DEVELOPMENT.md`）の該当節だけを読む。
2. 対象のPR本文またはコミットメッセージを読み、変更が主張する目的・不変条件・未確認事項を書き出す。
3. 読む節を決める。

   ```sh
   uv run --python 3.12 python .agents/skills/review-picoagent-changes/scripts/regression_hints.py <範囲>
   ```

   `python3` を直接使える環境ではそれでもよい。出力は手掛かりで、該当なしでも下の共通観点は省略しない。
4. `references/regression-catalog.md` の該当節を読む。各節の「固定済み」は機械検査が既にある範囲なので、手で再検査せず検査の穴だけを見る。

## 読む

差分を上から順に読むのではなく、変更された関数ごとに次を行う。

1. **主張と実装を照合する。** PR本文・コミットメッセージが言う修正が、全経路で本当に成り立つか。「直した」と書かれた経路の隣に同じ欠陥が残っていないか。
2. **呼び出し元と全経路を追う。** 正常・失敗・中断・タイムアウト・再初期化・設定変更直後・キャラや表示形式の切替直後を、`rg` で呼び出し元を列挙して確かめる。
3. **共通観点を必ず見る。** 過去に最も再発した型で、どの差分にも当てはまる。
   - 利用者が指示していないフォールバックが無いか（`AGENTS.md`。当て方は下の「フォールバックとコピペを当てはめる」）。
   - コピペで作った類似コードが無いか（`AGENTS.md`。当て方は同じ節）。
   - 読めない・壊れた入力を空で続け、その空を保存へ流していないか（D1）。
   - 失敗を `continue`・早期 `return`・空 `catch`・ログだけで済ませていないか。「解釈できない」が「指定なし」と同じ値へ落ちていないか（D2）。
   - 独立した後処理を1つの `try` にまとめ、前段の失敗で後段が飛ばないか（D3）。
   - 確保したプロセス・タイマー・リスナ・URLが全経路で解放されるか（D4）。
   - `cfg`・feature付きのコードとテストが対応3OSと全featureで検査されるか（D5）。
   - 追加したテスト・ガードが、退行を仕込むと本当に落ちるか（D6）。
   - 変える行の導入理由を `git log -L <開始>,<終了>:<ファイル>` かコメント・PR本文で確かめたか（D14）。
   - 会話に関わる変更なら、回答本文・履歴・読み上げが同じ公開済みの本文になり、全プロバイダのメッセージ形式を満たし、キャラ切替後に前のキャラの文脈が残らないか（D7・D8・D21・D22）。
   - 画面に関わる変更なら、操作部品が窓の内側・親の overflow の内側・前面要素に覆われない、の3条件を満たし、現行の全キャラ×全形式で崩れないか（D17〜D20）。
4. **台帳の該当節を当てる。** 「見る」の質問を差分へそのまま当て、該当した行を記録する。
5. **同型を全体から探す。** 1件見つけたら、同じ書き方・同じ責務を `rg` で全体検索する。過去に同型が別ファイルへ残っていた例: タイムアウトの待ち切り（`whisper_transcribe` と `meeting_recorder`）、曜日の語彙（`alarm` と `scheduler`）、通知取得の無言失敗（目覚ましと日常通知）。見た目の不具合は現行の全キャラクターで確認する。
6. **文書と照合する。** 担当文書と食い違うときは文書を正としてコードを疑う。文書自体が誤っていると判断したら、該当箇所と推奨する訂正を利用者へ報告する。

## フォールバックとコピペを当てはめる

規則の正本は `AGENTS.md`（「エラー処理・リソース」のフォールバック禁止、「進め方」のコピペ禁止）。ここではレビューでの当て方だけを書く。差分だけでなく、触れた関数の既存コードにも当てはめる。

- **フォールバック**:
  - 失敗・欠損・未対応の分岐を `rg` で列挙し、別手段への切替・降格・読み替え・飛ばしになっていないかを見る。`// フォールバック許可:` も手掛かりにする。
  - 許可には、`AGENTS.md` が定める根拠（会話・PR本文・文書に明記された利用者決定）が要る。辿れたら、指摘表の「対応・根拠」へ書く。辿れなければ撤去を指摘する。コメントの有無だけで判定しない。
  - 重要度: 利用者に見えない形で別の結果を見せる・保存するものはP1。表示だけが既定値へ落ちるものはP2。新しく足されるフォールバックは通さない。
- **コピペ**:
  - 1件見つけたら、特徴的な文字列・呼び出しの並び・定数で全体を `rg` し、同型を表にして列挙する（「読む」5.と同じ扱い）。
  - 写しの片方だけに修正が入り、もう片方に既知の不具合が残るものはP1。動作が同じで保守だけを難しくする重複はP2。新しく足されるコピペは通さない。
  - 共通化した関数のテストは、各呼び出し元の条件を表形式でまとめる。呼び出し元ごとに写さない。
  - 共通化しないと判断したものは、理由を「確認して問題なし」へ書く。

## 判定する

- 実害の経路（どの入力・操作・状態で、利用者に何が起きるか）を具体的に辿れたものだけを指摘にする。辿れない懸念は「確認」として実際に確かめ、問題が無ければ「確認して問題なし」に記録する。
- 重要度:
  - P0: データ消失、起動不能、秘密値・人格プロンプトの露出、販売物への開発用表示の混入。
  - P1: 機能が黙って動かない、誤った内容を見せる、プロセスやリソースが残る、特定OSで壊れる。
  - P2: 一部条件での表示崩れ・競合、検査の穴、文書のずれ、dead code。
  - P3: 命名・表記・軽微な一貫性。
- 意図的な設計を不具合と取り違えない。CSSの `pointer-events:none`、待ち時間、掃除範囲のように、変えると別の利用者体験が壊れる値は、導入理由を確かめてから判断する（D14）。

## 見た目の指摘を扱う

利用者の画像・目視・撮影QAで見た目の指摘が出たら、直す前後に次を行う。見た目の退行は「検査が見ていなかった条件」で再発してきたため、目視の合格だけで閉じない。

1. **同じ画面を再現する。** キャラ・表示形式・窓寸法・UIモードと明暗・画素密度・モニターを特定し、同じ条件で撮る。手段は `tools/screenshots/ui-check.mjs`、全員の一覧は `review-board.mjs --capture`、設定画面は `settings-display.mjs`、Live2D・MMD・CSP・実座標が絡むものは `verify-picoagent-ui` の実WebView2手順。
2. **型と見逃した理由を決める。** 台帳の D17〜D20 から型を選び、既存の検査がなぜ通したか（窓内の矩形だけを見た、親の overflow を見ない、前面要素の遮蔽を見ない、対象キャラが一部だけ、固定寸法だけ、プレビューと本体で式が違う）を書く。
3. **全員・全形式へ広げる。** 指摘が1体・1形式でも、`UI_CHECK_CHARACTERS=all` で配信コピーに実在する全キャラ×3形式を検査し、変更した画面の狭い寸法・最小寸法・2モード×明暗も見る。Live2D・MMDなどヘッドレスで撮れないキャラは実機で確かめるか、未確認として書く。
4. **機械検査で固定する。** 指摘ごとに `ui-check.mjs`・`settings-display.mjs`・`tools/tests/*.mjs` のいずれかへ、修正前の状態で落ちる検査を足す。検査の判定関数そのものに穴があった場合は、個別ケースを足すのではなく判定関数を直す（例: `fullyInside()` に親の overflow と前面要素の遮蔽を加えた）。表情の自然さのように数値にできない品質だけを目視とし、修正前後の比較画像の所在をPR本文へ書く。
5. **意図した重なりを明記する。** 配信でキャラの右側がチャットと重なる、トーストがクリックを通す、のように仕様上の重なりは、検査の例外と理由をコードのコメントか仕様文書に書き、検査を緩めて黙らせない。
6. 新しい型だったら台帳の D17〜D20 へ追記する。

## 会話の指摘を扱う

利用者の会話ログ・画面・読み上げで「返答がおかしい」と指摘されたら、直す前後に次を行う。会話の退行は、最適化や後処理の変更が別の言い回し・別のプロバイダ・別のキャラで効かなくなる形で再発してきた。

1. **同じ会話を再現する。** 発話の原文、直前の利用者発話と回答、選択キャラ、プロバイダとモデル、先回り実行が動いたか、`app.log` の該当ターンを特定する。モデル呼び出しを含まない部分（先回りの選択、メッセージ列の組み立て、後処理、履歴保存）はテストで再現する。
2. **どの段で壊れたかを決める。** 選択（`intent_*`・スキーマの絞り込み）→ 組み立て（人格・記憶・履歴・内部資料）→ プロバイダ変換（role の交互・tool 呼び出し）→ 後処理（思考ブロック・漏れたツール呼び出し・`guard_public_answer`）→ 表示・読み上げ・履歴保存、のどこかを特定する。モデルの気まぐれで片付けない。台帳の D7・D8・D21・D22 から型を選ぶ。
3. **言い回しと条件を広げる。** 当たるべき言い回し（漢字・ひらがな・催促・助詞違い・敬語・誤字）と、当たってはいけない近い言い回し（「今何時間働いた？」「ロンドンは今何時？」のような例）の両方で確かめる。後処理と組み立ての変更は、全プロバイダの変換（`local` の正規化、OpenAI互換、Anthropic、CLI）と、全キャラの人格で確かめる。
4. **機械検査で固定する。** 先回りの誤爆はスキル側のテストへ当たる例と当たらない例を、組み立て・後処理・履歴の不具合は該当モジュールの単体テストか `tools/tests/*.mjs` を、修正前に落ちる形で足す。同じ型が別の経路で再発したなら、出口ごとの対処を足さず受け口へ集約する（人格プロンプトの混入除去を `agent::guard_public_answer()` へ集めた #266 の方針）。
5. **費用のかかる実モデル確認は限る。** 実モデルでの確認は `local` を使い、OpenAI 互換など費用が発生するプロバイダは利用者の指示がある場合だけ使う（`AGENTS.md`）。確認できなかったモデル・プロバイダはPR本文の未確認へ書く。
6. 新しい型だったら台帳の D21・D22 へ追記する。

## 直す

1. `origin/main` から目的別ブランチを作る。レビュー対象のPRが未マージで自分の作成物ならそのブランチへ直接直し、他人の未マージPRなら変更を提案して作者の判断を待つ。
2. P0〜P2は同じ作業内で直す。見つけた同型も直す。方針判断が要るものも妥当な既定を選び、採否・理由・代替案をPR本文へ書く。
3. 直した不具合ごとに回帰テストを足すか、既存テストで固定済みであることを示す。追加したテストは修正前のコード（または退行を仕込んだ状態）で落ちることを確かめる。実装の言い換えだけのテスト、既存ガードと同じ検査の写しは足さない。
4. 同じ型が3回以上再発しているなら、テストではなく `mod guard`（走査は `crate::guard_scan`）か共通層への集約で構造的に防ぐ案を検討する。
5. 実機・外部資産が無くコードで解消できないものだけを残し、再現条件と着手条件を `docs/TASKS.md` へ書く。
6. 恒久ルールに値する再発防止策は `AGENTS.md`、新しい型のデグレは `references/regression-catalog.md` へ同じPRで追記する。

## 検証する

変更が出揃ってから、影響に合う段だけを最小回数で実行する。

1. `cargo check --manifest-path src-tauri/Cargo.toml`
2. `cargo test --manifest-path src-tauri/Cargo.toml --lib`（xtaskを変えたら `cargo test --manifest-path xtask/Cargo.toml` も）
3. UIを変えたら `node --test tools/tests/*.mjs` と `node --check <変更したJS>`
4. `cfg`・featureを変えたら他OSのtargetでも `cargo clippy --all-targets -- -D warnings` を確かめる。clippyは件数だけでなく出力の中身を読む。
5. 最終確認は `cargo xtask verify`。git-lfsが無い環境（Claude Code on the webのコンテナなど）ではキャラクター素材の検査が落ちるため、その失敗が素材由来であることを確かめてPR本文の未確認へ書く。
6. 画面の見た目・配置・起動表示が変わる場合は、`UI_CHECK_CHARACTERS=all node tools/screenshots/ui-check.mjs`（`PLAYWRIGHT_MODULE` の指定は `tools/screenshots/README.md`）を実行し、残った画像を開いて目視する。設定画面を変えたら `settings-display.mjs` も実行する。キャラ素材とPIXIが必要なので、未取得なら `git lfs pull`、`cargo xtask sync-characters`、`cargo xtask setup pixi` を先に行う。実WebView2が要るものは `verify-picoagent-ui` を使い、確認できなかった範囲は利用者の目視に委ねる範囲として分けて書く。

## 記録する

PR本文をレビュー記録の正本にし、別のMarkdown台帳へ複写しない。次の形で書く。

```markdown
## 対象
<範囲・コミット・PR番号>。読んだ観点: 共通観点、D1、D3、…

## 指摘と対応
| # | 優先 | 指摘 | 判定 | 対応・根拠 |
|---|---|---|---|---|
| 1 | P1 | <どの条件で利用者に何が起きるか> | 対応済み | <修正内容、回帰テスト名> |

## 見送り・保留
| # | 内容 | 判定 | 理由・着手条件 |

## 確認して問題なし（再走査を省くため）
- <観点>: <根拠>

## 検証
- 実行: <コマンドと結果>
- 未確認: <実機・GUI・外部サービスが要るもの>
```

その後は `AGENTS.md` の「PR とマージ」に従い、コミット、push、PR作成、squash merge、ブランチ削除まで行う。利用者が「マージしない」「PRだけ」と明示した場合は従う。
