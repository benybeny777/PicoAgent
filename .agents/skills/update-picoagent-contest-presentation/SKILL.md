# PicoAgent社内AIコンテストPPTを更新する

## 適用範囲を限定する

- このスキルは社内AIコンテスト用PPTだけに使う。一般的な紹介用PPT、LP、READMEの訴求ルールへ広げない。
- 利用者が明示した指示だけをルールとして扱う。作業エージェントの提案、推測、検証中の一時判断を恒久ルールへ追加しない。
- 新しい訴求やルールが必要に見えても勝手に追加せず、利用者へ確認する。
- PPTの編集と公開は`C:\00_PG\21_PicoAgent-LP`だけで行う。本体リポジトリ`C:\00_PG\20_PicoAgent`は内容確認にだけ使い、変更しない。
- PDFは作成しない。

## 必須の構成を守る

- ページ数はまだ決めていないため、スキル側で固定しない。
- ①エージェント名、②目的・課題、③利用シーン、④入力、⑤処理概要、⑥出力、⑦使い方、⑧構成要素、⑨工夫・独自性、⑩アピールポイント、⑪実行結果・効果、⑫制約・注意点をすべて含める。
- 構成の流れは「①②」「③⑦」「④⑤⑥」「実画面」「⑧⑨」「⑩⑪⑫」を基準にするが、各まとまりを1ページずつに固定しない。
- 本来は1枚が望ましいコンテスト資料だが、実際には他の応募者も数枚で作っているため、1枚へ固定しない。
- 文字とレイアウトを詰め、ゆったりしすぎたページを統合して全体の枚数を少し減らす。ただし、高機能で説明量が多いことによる必要な枚数は許容する。
- 「ギュッとする」は、余白、文字組み、配置を詰めて情報密度を上げる意味とする。実画面や動画を小さくしてぼかさない。
- 構成は以前の版から大きく変えない。利用者が不採用とした版を土台にしない。
- 1行タイトルを折り返さず、文字を小さくしすぎない。

## AIの処理概要を手厚くする

- 処理概要は枚数が増えても手厚く説明する。
- 人格処理は技術課題として扱わず、文脈、関係性、記憶、口調を組み立てるAIロジックの一部として説明する。
- AIの分担、合議、統合のロジックを審査上のアピールとして分かるようにする。必要なら図解する。
- Web検索と情報照合を必要に応じて行うことを含める。
- AIの数え方に「1人」など不自然な単位を使わない。
- 最終統合を黒帯やダークパネルにしない。

## 目的と対象を正しく示す

- ②目的・課題では、個人の趣味の延長として、ゲーミングPC向けのローカルLLMとマスコットを組み合わせた軽量Agentから始めたことを書く。
- 業務効率化を目的に始めたものではなく、機能拡張によって「Pico」と呼ぶ規模を超えたことを書く。
- 現在も主対象はゲーミングPCユーザーとして扱う。対象を一般ユーザー中心へ勝手に置き換えない。
- 一般利用者向けの利用手順や単一の利用例より、AIロジック、技術構成、多機能性、審査上のアピールを優先する。
- 議事録は多数ある機能の一つ、おまけの利用例として扱い、ページや訴求の中心にしない。できることをジャンル別に示す方を優先する。
- 外部AIを使わずローカル完結を選べるため、社内の機密データをクラウドAIへ渡さず端末内で処理でき、ビジネス利用にも耐えうるコアへ発展したことを示す。
- キャラクター生成では、一枚絵から分離原画、表情差分、動きへ展開し、本人性と画質を保つ工程が実際の技術課題であることを示す。

## 製品の売りを正しく示す

次を機能上の主な売りとして扱う。

- キャラクターが動く。
- 多数の機能を備える。
- マルチエージェントで分担、合議、統合できる。
- ローカルLLMで完結でき、対応LLMはGemmaだけに限定されない。
- FreeTokenは開発中の予定として扱う。対応完了後は、搭載VRAM容量を超える大容量モデルの実行にも対応予定と書き、現行公開版で対応済みとは書かない。
- ChatGPT／Claudeの契約枠をCodex CLI／Claude Codeから使う場合、契約プランの利用上限内ならAPI従量課金を気にせず使える。
- PicoAgent自身を使ってコネクタを開発し、機能を追加できる。
- OS・Tauri非依存の共通コアを分離しており、Web・スマホ展開の土台として再利用しやすい。

- 技術的に実装済みで、設定から有効化して使える機能は「できる」と書く。既定OFFを未対応や利用不可として扱わない。
- PC・ブラウザ操作、API、MCPの既定OFFに触れる場合は、⑫制約・注意点で「セキュリティのため既定OFF。設定から有効化して利用可能」と書く。主な売りの欄へON／OFF説明を置かない。
- プレゼン資料では、できないことや未対応事項を必要なく並べない。必須の制約は中立的にまとめ、実装済み機能の訴求を弱めない。
- MCPの記述は禁止しない。外部連携のおまけとして扱い、主な売りや⑩アピールポイントの中心にしない。
- 「製品全体を簡単にスマホ展開できる」と書かない。普通のスマホでそのまま動くような表現を避け、共通コアの再利用性に限定する。
- 共通コアへ人格処理やエージェント全体まで完全分離済みとは断定しない。
- 公開バイナリの利用者が無コードでRustコネクタを追加できるとは書かない。
- 「CLIサブスク」のような省略表現を使わない。
- API従量課金を必ず回避できるとは断定しない。
- 「Genspark相当」のような根拠のない比較、「技術の新規性」、Node不要をメリットとして追加しない。
- 「最速の方式を自動選択」は利用者から変更指示がない限り、そのままにする。
- 商品化しない、将来性がない、実用性がないなどの余計な表現を追加しない。

## 技術構成とレイアウトを守る

- 技術スタックは情報量に応じて単独ページにしてよい。Rust、Tauri 2、llama.cpp、Ollama、Whisper、AivisSpeech、通常2D、Live2D、THA3、画面・PC・ブラウザ操作、FreeTokenの予定を役割別に整理する。
- AivisSpeechは`AivisSpeech（VOICEVOX互換API）`と表現する。任意の互換音声エンジンを公式対応しているとは断定しない。
- 画面・PC・ブラウザ操作は機能として記載してよい。必要以上にクリックなど個別操作を主役にせず、できない旨を追加しない。
- AIロジック、技術構成、実画面などのページへ、関係の薄い「機能拡張／HTTP API／MCP」の帯を追加しない。
- AIロジックと技術構成へ黒い説明枠を追加しない。
- 実画面と動画の位置、サイズを変えない。
- 配信は多数あるレイアウトの一つとして扱い、製品全体の中心機能のように書かない。
- APIキー暗号化をWindows限定と書かない。
- PCスペックではメインメモリだけを強調せず、ローカルLLMに重要なVRAMを重視する。
- macOS版は最終調整中である旨を示す。
- 個人の趣味で開発したもので、実用性などを追求したものではない旨の免責は、1枚目のPPT内だけに置く。LPやREADMEへ広げない。

## プレビューと公開条件を守る

- PPTはスマホから確認できるようにする。更新のたびにREADMEのキャッシュ回避トークンを新しい値へ変える。
- PowerPointで全ページをMeiryoのまま1600×900 PNGへ書き出し、実際のページ数に対応する連番プレビューを差し替える。
- PPTのテキスト、図形、座標、フォント指定を変えずにプレビューだけを再出力する依頼では、PPT自体を編集しない。
- READMEではPPTリンク、スマホ用Office Viewerリンク、全ページのプレビューを同じキャッシュ回避トークンへ揃える。
- GitHub Actionsは作成、有効化、実行しない。
- ソースコード、`AGENTS.md`、スキル、内部資料、作業用スクリプトを公開リポジトリへ追加しない。
- 公開履歴を1コミットに保つよう利用者から指定されている場合は、作者を`beniya <benybeny777@gmail.com>`、メッセージを`公開版スナップショット`のままamendし、リモートの現在値を確認してから更新する。
- `v1.0.2`の移動を指定された場合はmainと同じコミットへ付け替え、タグに紐づくReleaseとセットアップEXEには触れない。
