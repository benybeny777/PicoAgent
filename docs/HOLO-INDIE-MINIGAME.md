# holo Indie応募のミニゲーム案（検討メモ）

この文書は、holo Indieの審査で最大の未確定点になっている**「ゲームとしての面白さ」をどう作るか**の検討メモです。実装ルールではありません（ルール正本は[AGENTS.md](../AGENTS.md)、現行仕様は[SPEC.md](../SPEC.md)、取引条件の検討は[docs/IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md)）。ここに書いた案はどれも未実装で、採否は未決です。

前提は[IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md) §1・§8-1のとおりです。現行ガイドラインの「デジタルゲーム」の定義にPicoAgentは当てはまりますが、**定義に当てはまることと審査合格は別**で、応募には企画書と概ね遊べるビルドの両方が要ります。この文書は後者に何を載せるかを決めるためのものです。

---

## 0. 結論

- **1本の大作を作らない。** 常駐アプリの強みは「一日中そばにいる」ことで、単体のゲーム画面へ閉じた瞬間、グラフィック量とボリュームで他の二次創作ゲームと正面から比べられます。そこは勝てません。
- 推奨は**三層構成**です。**(1) 常駐でしか成立しない遊び（案1）** で独自性を示し、**(2) ルールが確定した短時間の対戦（案4）** で「確実に遊べる」を担保し、**(3) 集中タイマー連動の進行（案3）** で続ける理由を作ります。
- **案2（配信ごっこ）は魅力が最大ですが、初回応募には載せません。** 台詞量が最も多く、タレント名義の発言リスクと監修コストが跳ね上がります。三層が動いた後の二手目にします。
- **どの案でも、ゲーム中の台詞はスクリプトを正本にし、LLM生成を混ぜません。** これは手抜きではなく、**監修できる状態で持ち込むための設計**です（§4）。
- 審査版ビルドは読み上げが無効で音声モデルを含まないため、**全案が無音で成立することを必須条件**にしています（[開発ガイド](DEVELOPMENT.md#holo-indie審査への限定共有版windows)）。

## 1. 案の一覧

### 案1. デスクトップかくれんぼ（推奨・主軸）

| | |
|---|---|
| 遊びの中核 | キャラが「かくれんぼ」を宣言し、透過ウィンドウが画面の隅や端へ小さく移動して半分だけ見える状態になる。利用者が見つけてクリックすると発見成立。連続発見・発見までの時間で記録が伸びる |
| 操作 | クリックのみ。呼び出しホットキーで降参もできる |
| 使う既存機能 | ウィンドウ移動・表示／非表示（`hotkey.rs`・`layout.rs`）、キャラ構図（`PICOAGENT_CHARACTER_FRAMING`）、表情モーフと待機姿勢、感情状態 |
| 新規実装 | 隠れ場所の決定（作業領域を避ける判定）、発見判定、記録と連続日数の保存、開始条件と頻度の設定項目 |
| 強み | **他のプラットフォームでは作れない。** デスクトップ常駐そのものが遊具になる。台詞が短く監修が容易で、無音で完全に成立する。企画書で「なぜアプリなのか」に一行で答えられる |
| 弱み・リスク | ゲームとしては薄いと見られる可能性がある。**作業妨害と紙一重**なので、全画面アプリ実行中・会議中は開始しない、頻度を選べる、常にオフにできる、を設計に含める。オフにできない仕様は採らない |
| 概算 | 小（3〜5人日） |

### 案2. 配信ごっこ（魅力は最大・初回応募からは外す）

| | |
|---|---|
| 遊びの中核 | 配信形式の画面でキャラが配信枠を回す。利用者は企画カード（雑談／ゲーム実況／歌枠／告知）を選び、コメント欄へ打ち込む。テンションとコメント密度が動き、1枠5分前後で結果カードが残る |
| 操作 | カード選択とテキスト入力 |
| 使う既存機能 | 配信形式、背景内ディスプレイ、配信背景（ゲーム部屋等）、字幕テロップ、感情状態 |
| 新規実装 | 枠進行のステートマシン、コメントの定型プール、結果の集計と収集要素 |
| 強み | **ホロライブの文脈そのもの**で、審査側に「何の遊びか」が一瞬で伝わる。既存の配信形式と背景がほぼそのまま使える |
| 弱み・リスク | **台詞量が全案で最大。** 監修対象が膨らむ。AI生成の台詞を混ぜるとタレント名義の発言事故に直結する。同時接続数やスーパーチャットを模した表現は誤認と金銭表現の点でデリケートなので、**収益表現は扱わない**前提にする |
| 概算 | 中〜大（10〜20人日） |

### 案3. 今日のミッション（集中タイマー連動・推奨）

| | |
|---|---|
| 遊びの中核 | 25分の集中が1ステージ。達成するとキャラの部屋の模様替え、ポーズ、背景が解放される。週の目標達成でまとめて解放 |
| 操作 | 既存の集中タイマー操作のまま。ゲーム側は結果表示と解放物の選択だけ |
| 使う既存機能 | `focus_timer`、`praise_log`、`todo_plan`、`reminder`、配信背景の切替、キャラ別構図 |
| 新規実装 | 進行と解放物の保存、解放演出、部屋の見た目の差し替え |
| 強み | **アプリの実用価値をそのままゲーム進行に変換できる。** 提案書の売りである「接触時間の長さ」（[IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md) §2-1）と一貫し、長期プレイの理由になる |
| 弱み・リスク | これ単体だと「ゲームか？」という審査の核心にそのまま突き当たる。案1・案4と必ずセットで出す。解放をランダム抽選にする場合も**有償要素とは結び付けない**（§5の未確定事項） |
| 概算 | 中（7〜12人日） |

### 案4. 二人卓（短時間対戦・推奨）

| | |
|---|---|
| 遊びの中核 | ルールが確定した短時間の対戦を数種。五目並べ、神経衰弱、数字当て（ヒット＆ブロー）など。キャラは表情と短い定型台詞で反応し、強さを3段階から選ぶ |
| 操作 | クリックまたは数字入力 |
| 使う既存機能 | 表情モーフ、ポーズ切替、既存のフキダシと履歴表示 |
| 新規実装 | 盤面の描画と入力、思考ルーチン（探索が浅くて済むものを選ぶ）、定型台詞プール |
| 強み | **確実に完成する。** 仕様が枯れていてバグりにくく、審査ビルドで「起動してすぐ遊べる」を担保できる。台詞が完全定型なので**監修が最も楽** |
| 弱み・リスク | 独自性は低く、これ単体では審査の決め手にならない。**推しと遊んでいる感**を出せるかは表情と台詞の質にかかる |
| 概算 | 小（1種あたり2〜4人日） |

### 案5. ◯◯検定（クイズ・タイピング／条件付き）

| | |
|---|---|
| 遊びの中核 | 推しに関するクイズと、コメント入力を模したタイピング |
| 使う既存機能 | 既存の入力欄と履歴、表情 |
| 新規実装 | 問題データの読み込みと出題、判定、記録 |
| 強み | ファン向けの満足度が高く、実装は軽い。無音で成立する |
| 弱み・リスク | **問題データは監修済みのものだけを使い、LLMに問題を作らせない。** 誤情報を出せば「タレントに嘘を言わせた」ことになる。データが枯れるとすぐ飽きる |
| 概算 | 小〜中（4〜8人日＋データ作成） |

### 案6. 実況してもらう（将来案・初回応募からは外す）

| | |
|---|---|
| 遊びの中核 | 利用者が別のゲームを遊んでいる間、画面取得でキャラが実況・応援する |
| 使う既存機能 | 画面取得、`view_image`、感情状態 |
| 強み | **極めて独自。** 「推しに実況される」という体験は他にない |
| 弱み・リスク | **発話がAI生成そのもので、§5の懸念（想定外の発言が切り抜かれる）に正面から当たる。** 監修の方法が立たないため、人格ロックと話題ガードが実装され、監修側の合意が取れるまで審査ビルドへ載せない |
| 概算 | 中（ただしリスクで保留） |

### 採らない案

- **リズムゲーム・ペンライト。** 審査版は音声モデルとAivisを含まず読み上げも無効なので、音に合わせる遊びが成立しません。自作BGMを足せば形にはなりますが、**音のない状態で判断される審査ビルドで最も損をする形式**です。
- **通知やウィンドウを敵に見立てる防衛ゲーム。** 実用アプリとしての挙動と衝突し、誤って業務の通知を消す事故につながります。

## 3. 推奨する提出形（第1次）

**案4を1〜2種 → 案1 → 案3**の順に作り、3つが動いた状態で応募します。この順にする理由は、**途中で時間切れになっても常に「遊べるビルド」が手元にある**ためです。案1から作ると、完成するまで遊べる画面がひとつもない期間が続きます。

企画書では次の順で説明します。

1. PicoAgentは常駐アプリで、**一日中そばにいることが遊びの土台**である（案1・案3の説明になる）。
2. 起動してすぐ遊べる卓がある（案4）。
3. 続ける理由として、日々の集中が進行に変わる（案3）。
4. 次の段階として配信ごっこ（案2）を置き、**監修の前提が整ってから着手する**と明記する。

## 4. どの案でも守る共通設計

- **ゲーム中の台詞はスクリプトを正本にし、LLM生成を混ぜない。** 監修担当が「何を喋るか」を全部読める状態にするための設計です。AIの返答とゲームの台詞は発生源を分けます。
- **人格ロック、話題ガード、AI生成である旨の常時表示とセットで出す。** 3件とも未実装です（[IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md) §7）。ゲームだけ先に作っても監修の前提を満たしません。
- **音声なしで成立させる。** 効果音やBGMを足す場合は、第三者素材の利用条件を先に揃えます（[docs/TASKS.md](TASKS.md) の販売ゲート「第三者資産」と同じ扱い）。
- **作業を妨げない。** 全画面アプリの実行中は開始しない、頻度を選べる、常にオフにできる、進行は中断しても保存される。
- **課金とランダム要素を結び付けない。** 解放物の抽選を入れる場合も無償の範囲に閉じます（§5）。
- **配布境界を守る。** 実装は`ui/`配下と既存のCSP・`bundle_scope`の許可範囲で行い、外部CDNと`eval`に依存しません。保存は既存の設定・データ領域の作法に従い、審査版の専用領域（`com.picoagent.holo-indie-review`）を通常版と混ぜません。
- **MMDの表現範囲に収める。** 現行のMMD描画はボーン姿勢・表情モーフ・まばたき・音量連動の口モーフまでで、**VMDモーション再生と剛体物理は対象外**です（[SPEC.md](../SPEC.md#mmdキャラクター)）。勝利演出などはポーズと表情の切替、構図の寄りで作ります。

## 5. 未確定（一次情報で確認してから決める）

1. **応募締切と提出物の形式。** 既存メモでは年3回（1月・5月・9月）で企画書と概ね遊べるビルドが必須、とあります。応募の直前に必ず最新のエントリーページを読み直します。
2. **アプリ内課金、ランダム抽選、外部通信の可否。** 解放物の抽選と、AIプロバイダへの通信を伴う常駐機能が審査条件に触れないかを確認します。
3. **支給モデルをゲーム演出へ使える範囲。** ポーズ追加や表情差分の作成が、貸与条件の中でどこまで許されるか。
4. **本体無料方針との整合。** [docs/SALES.md](SALES.md) §4は本体無料・キャラ課金ですが、holo Indieは有償の二次創作ゲームを扱う枠です。**holo Indie版を別SKUの買い切りとして出すのか、本体無料のまま出せるのか**は、還元の仕組みと合わせて確認が要ります。
5. **監修の単位。** 台詞プール全体を一括で見てもらうのか、ゲームごとに分けるのか。工数見積もりがここで変わります。
