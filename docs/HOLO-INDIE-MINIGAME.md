# holo Indie応募のミニゲーム案（検討メモ）

この文書は、holo Indieの審査で最大の未確定点になっている**「ゲームとしての面白さ」をどう作るか**の検討メモです。実装ルールではありません（ルール正本は[AGENTS.md](../AGENTS.md)、現行仕様は[SPEC.md](../SPEC.md)、取引条件の検討は[docs/IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md)）。ここに書いた案はどれも未実装で、採否は未決です。

前提は[IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md) §1・§8-1のとおりです。現行ガイドラインの「デジタルゲーム」の定義にPicoAgentは当てはまりますが、**定義に当てはまることと審査合格は別**で、応募には企画書と概ね遊べるビルドの両方が要ります。この文書は後者に何を載せるかを決めるためのものです。

---

## 0. 結論

- **1本の大作を作らない。** 常駐アプリの強みは「一日中そばにいる」ことで、単体のゲーム画面へ閉じた瞬間、グラフィック量とボリュームで他の二次創作ゲームと正面から比べられます。そこは勝てません。
- 推奨は**四層構成**です（§3）。**入口**（案11・案4）で起動してすぐ遊べることを示し、**常駐の独自性**（案13・案1）でこのアプリでしか作れない遊びを見せ、**続ける理由**（案7・案3）で毎日触る動機を作り、**外へ出る**（案12）で遊んだ結果を画像として残します。
- **案2（配信ごっこ）は魅力が最大ですが、初回応募には載せません。** 台詞量が最も多く、タレント名義の発言リスクと監修コストが跳ね上がります。四層が動いた後の二手目にします。**案8（ふれあい）も同じ扱い**で、接触表現の線引きを監修側へ確認してから入れます。
- **どの案でも、ゲーム中の台詞はスクリプトを正本にし、LLM生成を混ぜません。** これは手抜きではなく、**監修できる状態で持ち込むための設計**です（§4）。
- 審査版ビルドは読み上げが無効で音声モデルを含まないため、**全案が無音で成立することを必須条件**にしています（[開発ガイド](DEVELOPMENT.md#holo-indie審査への限定共有版windows)）。

## 1. 案の一覧

### 案1. デスクトップかくれんぼ（推奨・主軸）

| | |
|---|---|
| 遊びの中核 | キャラが「かくれんぼ」を宣言し、透過ウィンドウが画面の隅や端へ小さく移動して半分だけ見える状態になる。利用者が見つけてクリックすると発見成立。連続発見・発見までの時間で記録が伸びる |
| 操作 | クリックのみ。呼び出しホットキーで降参もできる |
| 使う既存機能 | ウィンドウ移動・表示／非表示（`hotkey.rs`・`layout.rs`）、キャラ構図（`PICOAGENT_CHARACTER_FRAMING`）、表情モーフと待機姿勢、感情状態 |
| 新規実装 | 隠れ場所の決定（作業領域を避ける判定）、発見判定、記録と連続日数の保存、開始条件と頻度の設定項目 |
| 強み | **他のプラットフォームでは作れない。** デスクトップ常駐そのものが遊具になる。台詞が短く監修が容易で、無音で完全に成立する。企画書で「なぜアプリなのか」に一行で答えられる |
| 弱み・リスク | ゲームとしては薄いと見られる可能性がある。**作業妨害と紙一重**なので、全画面アプリ実行中・会議中は開始しない、頻度を選べる、常にオフにできる、を設計に含める。オフにできない仕様は採らない |
| 概算 | 小（3〜5人日） |

### 案2. 配信ごっこ（魅力は最大・初回応募からは外す）

| | |
|---|---|
| 遊びの中核 | 配信形式の画面でキャラが配信枠を回す。利用者は企画カード（雑談／ゲーム実況／歌枠／告知）を選び、コメント欄へ打ち込む。テンションとコメント密度が動き、1枠5分前後で結果カードが残る |
| 操作 | カード選択とテキスト入力 |
| 使う既存機能 | 配信形式、背景内ディスプレイ、配信背景（ゲーム部屋等）、字幕テロップ、感情状態 |
| 新規実装 | 枠進行のステートマシン、コメントの定型プール、結果の集計と収集要素 |
| 強み | **ホロライブの文脈そのもの**で、審査側に「何の遊びか」が一瞬で伝わる。既存の配信形式と背景がほぼそのまま使える |
| 弱み・リスク | **台詞量が全案で最大。** 監修対象が膨らむ。AI生成の台詞を混ぜるとタレント名義の発言事故に直結する。同時接続数やスーパーチャットを模した表現は誤認と金銭表現の点でデリケートなので、**収益表現は扱わない**前提にする |
| 概算 | 中〜大（10〜20人日） |

### 案3. 今日のミッション（集中タイマー連動・推奨）

| | |
|---|---|
| 遊びの中核 | 25分の集中が1ステージ。達成するとキャラの部屋の模様替え、ポーズ、背景が解放される。週の目標達成でまとめて解放 |
| 操作 | 既存の集中タイマー操作のまま。ゲーム側は結果表示と解放物の選択だけ |
| 使う既存機能 | `focus_timer`、`praise_log`、`todo_plan`、`reminder`、配信背景の切替、キャラ別構図 |
| 新規実装 | 進行と解放物の保存、解放演出、部屋の見た目の差し替え |
| 強み | **アプリの実用価値をそのままゲーム進行に変換できる。** 提案書の売りである「接触時間の長さ」（[IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md) §2-1）と一貫し、長期プレイの理由になる |
| 弱み・リスク | これ単体だと「ゲームか？」という審査の核心にそのまま突き当たる。案1・案4と必ずセットで出す。解放をランダム抽選にする場合も**有償要素とは結び付けない**（§5の未確定事項） |
| 概算 | 中（7〜12人日） |

### 案4. 二人卓（短時間対戦・推奨）

| | |
|---|---|
| 遊びの中核 | ルールが確定した短時間の対戦を数種。五目並べ、神経衰弱、数字当て（ヒット＆ブロー）など。キャラは表情と短い定型台詞で反応し、強さを3段階から選ぶ |
| 操作 | クリックまたは数字入力 |
| 使う既存機能 | 表情モーフ、ポーズ切替、既存のフキダシと履歴表示 |
| 新規実装 | 盤面の描画と入力、思考ルーチン（探索が浅くて済むものを選ぶ）、定型台詞プール |
| 強み | **確実に完成する。** 仕様が枯れていてバグりにくく、審査ビルドで「起動してすぐ遊べる」を担保できる。台詞が完全定型なので**監修が最も楽** |
| 弱み・リスク | 独自性は低く、これ単体では審査の決め手にならない。**推しと遊んでいる感**を出せるかは表情と台詞の質にかかる |
| 概算 | 小（1種あたり2〜4人日） |

### 案5. ◯◯検定（クイズ・タイピング／条件付き）

| | |
|---|---|
| 遊びの中核 | 推しに関するクイズと、コメント入力を模したタイピング |
| 使う既存機能 | 既存の入力欄と履歴、表情 |
| 新規実装 | 問題データの読み込みと出題、判定、記録 |
| 強み | ファン向けの満足度が高く、実装は軽い。無音で成立する |
| 弱み・リスク | **問題データは監修済みのものだけを使い、LLMに問題を作らせない。** 誤情報を出せば「タレントに嘘を言わせた」ことになる。データが枯れるとすぐ飽きる |
| 概算 | 小〜中（4〜8人日＋データ作成） |

### 案6. 実況してもらう（将来案・初回応募からは外す）

| | |
|---|---|
| 遊びの中核 | 利用者が別のゲームを遊んでいる間、画面取得でキャラが実況・応援する |
| 使う既存機能 | 画面取得、`view_image`、感情状態 |
| 強み | **極めて独自。** 「推しに実況される」という体験は他にない |
| 弱み・リスク | **発話がAI生成そのもので、§5の懸念（想定外の発言が切り抜かれる）に正面から当たる。** 監修の方法が立たないため、人格ロックと話題ガードが実装され、監修側の合意が取れるまで審査ビルドへ載せない |
| 概算 | 中（ただしリスクで保留） |

### 案7. お留守番とおみやげ

| | |
|---|---|
| 遊びの中核 | アプリを閉じている間もキャラの時間は進む。次の起動時に「いない間なにをしていたか」の報告と、おみやげ（部屋に飾るアイテム、ポーズ、背景の小物）が1つ渡される。離れていた時間が長いほど内容が変わる |
| 操作 | 起動するだけ。受け取りのクリックのみ |
| 使う既存機能 | 起動時の初期化、キャラ別の履歴と関係性、配信背景の差し替え |
| 新規実装 | 経過時間から結果を決める抽選表、おみやげの保存と飾り付け、報告の定型文プール |
| 強み | **常駐アプリの「また会う」瞬間そのものを遊びにできる。** 実装が全案で最も軽く、無音で成立し、台詞が短い。毎日起動する理由になる |
| 弱み・リスク | 遊びの density は低く、これ単体では審査の答えにならない。**「留守中に本当は何もしていない」ことを隠す書き方にしない**（実際の行動として報告すると、後で監修側が問題視しうる。あくまで想像の出来事として書く） |
| 概算 | 小（2〜4人日） |

### 案8. ふれあい（なでる・おやつ／条件付き）

| | |
|---|---|
| 遊びの中核 | 立ち絵の頭や肩をクリック・ドラッグすると表情と姿勢が変わる。おやつを渡すと専用の表情が出る。得点も勝敗もない、触りごこちだけの遊び |
| 操作 | クリックとドラッグ |
| 使う既存機能 | 表情モーフ、ボーン姿勢、キャラ別構図、感情状態 |
| 新規実装 | 当たり判定の領域定義、反応の対応表 |
| 強み | **MMDの表情モーフがそのまま遊びになる。** 素材の追加がほぼ要らず、審査で「キャラが可愛く反応する」ことを最短で見せられる |
| 弱み・リスク | **接触表現は許諾側が最も神経を使う領域。** 触れる場所を頭と肩に限り、反応は定型に固定し、種類を増やさないことを設計で保証する。ここを曖昧にしたまま出すと、他の案の評価まで巻き添えにする。**初回応募では外し、監修側の線引きを聞いてから入れる** |
| 概算 | 小（2〜4人日） |

### 案9. しりとり

| | |
|---|---|
| 遊びの中核 | キャラと交互にしりとり。制限時間あり。語彙の被り、「ん」、未登録語の判定はすべて辞書で行い、AIに判定させない |
| 操作 | テキスト入力 |
| 使う既存機能 | 既存の入力欄と履歴表示、表情 |
| 新規実装 | 語彙データと読みの照合、重複判定、難易度（キャラ側の語彙量と返答の速さ） |
| 強み | **判定が決定論的で、LLMを一切通さない。** 誤判定も暴走もなく、監修対象は定型の煽り・褒め台詞だけ。配信文化とも地続きで、無音で完全に成立する |
| 弱み・リスク | 語彙データのライセンスを先に確定する（既存の日本語辞書を使うなら再配布条件の確認が要る。自前の語彙リストが最も安全）。遊びとしては地味 |
| 概算 | 小〜中（4〜6人日＋語彙データ） |

### 案10. 画面いろあつめ

| | |
|---|---|
| 遊びの中核 | キャラが「青いものを見せて」のようなお題を出す。利用者が自分の画面上の該当箇所をドラッグで囲むと、**選択領域の色をプログラムが判定**して正否が決まる。制限時間内に何個集められるか |
| 操作 | 画面上のドラッグ選択 |
| 使う既存機能 | 画面取得、`view_image` の表示経路 |
| 新規実装 | 範囲選択のオーバーレイ、色の判定（平均色と色相の範囲）、お題の生成 |
| 強み | **利用者のデスクトップそのものが盤面になる。** 毎回内容が変わり、常駐アプリでしか作れない。色の判定は計算で決まるのでAI判定の不確実さが無い |
| 弱み・リスク | **画面の内容を扱うので、取得した画像を外部へ送らず端末内だけで判定することを設計で担保する。** 業務画面を映す利用者がいる前提で、保存もしない。お題を「色」以外（物体名など）へ広げるとAI判定が必要になり、この長所が消える |
| 概算 | 中（6〜10人日） |

### 案11. 立ち絵の間違い探し

| | |
|---|---|
| 遊びの中核 | キャラが2回ポーズを取り、その間に表情・髪・小物のどこかが変わっている。どこが変わったかをクリックで当てる。段階が上がるほど差分が小さくなる |
| 操作 | クリック |
| 使う既存機能 | 表情モーフ、ボーン姿勢、`capturePreview` の撮影経路、キャラ別構図 |
| 新規実装 | 差分の組み合わせ表、当たり判定、段階の進行 |
| 強み | **素材の追加がゼロ。** 既にあるモーフとポーズの差分をそのまま問題に変換でき、**キャラの絵の良さを見せる遊びが最小工数で作れる**。無音で成立し、台詞もほぼ不要 |
| 弱み・リスク | モーフの種類が少ないモデルでは問題のバリエーションが尽きる。**支給モデルのモーフ数に出来が左右される**ので、実モデルで作れる問題数を先に数える |
| 概算 | 小（3〜5人日） |

### 案12. 今日のサムネ作り

| | |
|---|---|
| 遊びの中核 | 背景、構図、表情、ポーズ、文字を選んで「今日の配信サムネ」を1枚作り、保存する。お題（今日のテーマ）が日替わりで出て、作った枚数がアルバムに溜まる |
| 操作 | 選択と配置 |
| 使う既存機能 | 配信背景、背景内ディスプレイ、キャラ別構図、表情・ポーズ、`capturePreview` の撮影 |
| 新規実装 | 選択UI、文字入れ、アルバム保存 |
| 強み | **画像生成AIを使わずに成立する**（既存の描画を撮るだけ）。ファンが作って外へ出す導線になり、**IP側から見て宣伝効果という分かりやすい利点がある**。遊びの終わりに成果物が残る |
| 弱み・リスク | **出力画像を利用者が公開してよいかは二次創作ガイドラインの確認が要る。** 公開を想定するなら、作品名のクレジットを画像へ必ず入れる設計にする。使える背景・文字に不適切なものを入れられないよう、自由入力の扱いを決める（定型文からの選択が安全） |
| 概算 | 中（6〜10人日） |

### 案13. 起きるまで解けないアラーム

| | |
|---|---|
| 遊びの中核 | 設定した時刻にキャラが起こしに来る。止めるには短いゲーム（計算、並べ替え、色合わせ）を1問解く。解くとその日の記録が残り、連続日数で解放物が増える |
| 操作 | クリックまたは数字入力 |
| 使う既存機能 | `alarm`、`reminder`、`task_scheduler`、ホットキーとウィンドウ表示、表情 |
| 強み | **常駐アプリの実用機能がそのまま遊びの入口になる。** 毎日必ず1回遊ぶ理由ができ、継続率の説明が企画書で具体的になる。無音でも成立する（画面表示で起こす） |
| 弱み・リスク | **アラームを止められない事故は実害になる。** 何度も失敗したら解除できる逃げ道、ゲームを挟まない通常アラームとの併存、オフ設定を必ず用意する。ここを削ると実用機能の信頼を落とす |
| 概算 | 小〜中（4〜7人日） |

### 採らない案

- **リズムゲーム・ペンライト。** 審査版は音声モデルとAivisを含まず読み上げも無効なので、音に合わせる遊びが成立しません。自作BGMを足せば形にはなりますが、**音のない状態で判断される審査ビルドで最も損をする形式**です。
- **通知やウィンドウを敵に見立てる防衛ゲーム。** 実用アプリとしての挙動と衝突し、誤って業務の通知を消す事故につながります。

## 3. 推奨する提出形（第1次）

案7〜13を足した結果、**三層から四層へ広げます**。追加案のうち3つ（案11・案12・案13）は、当初の推奨より費用対効果が良いと判断しました。

| 層 | 何を示すか | 採る案 |
|---|---|---|
| **入口** | 起動してすぐ遊べる | **案11（間違い探し）**、案4（二人卓）1〜2種 |
| **常駐の独自性** | このアプリでしか作れない遊び | **案13（起きるまで解けないアラーム）**、案1（かくれんぼ） |
| **続ける理由** | 毎日触る動機 | **案7（お留守番とおみやげ）**、案3（今日のミッション） |
| **外へ出る** | 遊んだ結果が外に残る | **案12（今日のサムネ作り）** |

作る順は **案11 → 案7 → 案13 → 案4 → 案1 → 案12 → 案3** です。最初の2つが最小工数で、**着手から数日で「遊べるビルド」が手元にできる**ことを優先しました。案3は最も重いので最後に置きます。

当初の推奨からの変更点は3つです。

- **案11を先頭に置いた。** 素材の追加がゼロで、表情モーフの差分をそのまま問題にできます。**支給されたモデルの絵の良さを見せる遊び**でもあるので、審査で最初に触ってもらう画面として案4より向いています。
- **案13を案1と並べた。** かくれんぼは「遊びが薄い」と見られうるのに対し、アラームは**毎日必ず1回遊ぶ**構造で、継続率の説明が企画書で具体的になります。
- **案12を層として足した。** 遊んだ結果が画像として残り外へ出ていくので、**IP側から見た宣伝効果**という、他の案にはない利点を説明できます。

企画書では次の順で説明します。

1. PicoAgentは常駐アプリで、**一日中そばにいることが遊びの土台**である（案13・案1・案7の説明になる）。
2. 起動してすぐ遊べる（案11・案4）。
3. 続ける理由として、日々の集中と再会が進行に変わる（案3・案7）。
4. 遊んだ結果が1枚の画像として外へ出る（案12）。
5. 次の段階として配信ごっこ（案2）とふれあい（案8）を置き、**監修の前提と線引きが決まってから着手する**と明記する。

## 4. どの案でも守る共通設計

- **ゲーム中の台詞はスクリプトを正本にし、LLM生成を混ぜない。** 監修担当が「何を喋るか」を全部読める状態にするための設計です。AIの返答とゲームの台詞は発生源を分けます。
- **人格ロック、話題ガード、AI生成である旨の常時表示とセットで出す。** 3件とも未実装です（[IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md) §7）。ゲームだけ先に作っても監修の前提を満たしません。
- **音声なしで成立させる。** 効果音やBGMを足す場合は、第三者素材の利用条件を先に揃えます（[docs/TASKS.md](TASKS.md) の販売ゲート「第三者資産」と同じ扱い）。
- **作業を妨げない。** 全画面アプリの実行中は開始しない、頻度を選べる、常にオフにできる、進行は中断しても保存される。
- **課金とランダム要素を結び付けない。** 解放物の抽選を入れる場合も無償の範囲に閉じます（§5）。
- **配布境界を守る。** 実装は`ui/`配下と既存のCSP・`bundle_scope`の許可範囲で行い、外部CDNと`eval`に依存しません。保存は既存の設定・データ領域の作法に従い、審査版の専用領域（`com.picoagent.holo-indie-review`）を通常版と混ぜません。
- **MMDの表現範囲に収める。** 現行のMMD描画はボーン姿勢・表情モーフ・まばたき・音量連動の口モーフまでで、**VMDモーション再生と剛体物理は対象外**です（[SPEC.md](../SPEC.md#mmdキャラクター)）。勝利演出などはポーズと表情の切替、構図の寄りで作ります。
