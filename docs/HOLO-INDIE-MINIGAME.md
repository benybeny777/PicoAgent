# holo Indie応募のミニゲーム案（検討メモ）

この文書は、holo Indieの審査で最大の未確定点になっている**「ゲームとしての面白さ」をどう作るか**の検討メモです。実装ルールではありません（ルール正本は[AGENTS.md](../AGENTS.md)、現行仕様は[SPEC.md](../SPEC.md)、取引条件の検討は[docs/IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md)）。ここに書いた案はどれも未実装で、採否は未決です。

前提は[IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md) §1・§8-1のとおりです。現行ガイドラインの「デジタルゲーム」の定義にPicoAgentは当てはまりますが、**定義に当てはまることと審査合格は別**で、応募には企画書と概ね遊べるビルドの両方が要ります。この文書は後者に何を載せるかを決めるためのものです。

---

## 0. 結論

- **1本の大作を作らない。** 常駐アプリの強みは「一日中そばにいる」ことで、単体のゲーム画面へ閉じた瞬間、グラフィック量とボリュームで他の二次創作ゲームと正面から比べられます。そこは勝てません。
- **案1〜13は安全側に寄せすぎでした（§1-B）。** 台詞のAI生成リスクを避けて言葉のない小品ばかりにした結果、遊びとして地味になっています。避けるべきは「AIがその場で作る台詞」であって「書かれた台詞」ではありません。**脚本は監修する側にとって最も読みやすい形**です。
- **LLMを危険物として遠ざけたのも誤りでした（§1-C）。** 実際に動くAIエージェントを内蔵していることがこの製品の最大の差で、それを使わない企画ならこの製品で応募する意味が薄くなります。問われるのは使うか否かではなく、**LLMの出力のどれがタレントの発言として画面に出るか**です。判定層（構造化データ）とモブ層（視聴者コメント・資料・地の文）へ寄せれば、利点はほぼ全部取れます。
- 推奨は**案15（実時間で進む物語）を背骨、案17（推しに調べさせる推理）を目玉、案19（大喜利）を入口**に据える形です（§3）。小品（案11・案13・案7）は添えに降ろします。
- **審査ビルドは同梱のローカルLLMで完結させます。** 審査する側がAPI鍵を持っている前提には立てません。
- **案2（配信ごっこ）は二手目の筆頭です。** モブ層の導入で発言リスクは下がりましたが、台詞量が全案で最大で監修コストが重いので、入口・背骨・目玉が動いた後に着手します。**案8（ふれあい）は別の理由で見送り**で、接触表現の線引きを監修側へ確認してから入れます。
- **どの案でも、キャラの台詞だけは脚本とテンプレートを正本にします。** LLMは判定層とモブ層で自由に使い、**本人の発言としてその場で生成した文を出さない**、という線の引き方です（§1-C・§4）。
- 審査版ビルドは読み上げが無効で音声モデルを含まないため、**全案が無音で成立することを必須条件**にしています（[開発ガイド](DEVELOPMENT.md#holo-indie審査への限定共有版windows)）。

|---|---|

| 新規実装 | 隠れ場所の決定（作業領域を避ける判定）、発見判定、記録と連続日数の保存、開始条件と頻度の設定項目 |

### 採らない案

- **リズムゲーム・ペンライト。** 審査版は音声モデルとAivisを含まず読み上げも無効なので、音に合わせる遊びが成立しません。自作BGMを足せば形にはなりますが、**音のない状態で判断される審査ビルドで最も損をする形式**です。
- **通知やウィンドウを敵に見立てる防衛ゲーム。** 実用アプリとしての挙動と衝突し、誤って業務の通知を消す事故につながります。

## 1-B. 面白さを優先した案（第3弾）

案1〜13は**安全側に寄せすぎました**。台詞のAI生成リスクを避けようとして、言葉を使わない小品ばかりになり、遊びとしては地味です。判断の誤りは「脚本を書く」選択肢を外したことでした。**二次創作ゲームは脚本を書いて監修に出すのが普通で、脚本は監修する側にとって最も読みやすく、直しやすい形**です。避けるべきなのは「AIがその場で作る台詞」であって、「書かれた台詞」ではありません。

ここから先は、次の3つを使って面白さを取りに行く案です。**(1) 脚本を書く。(2) ウィンドウの中に閉じず画面全体を使う。(3) AIエージェントという他の二次創作ゲームが持っていない武器を、遊びの道具として使う。**

### 案14. デスクトップ・ボス戦

| | |
|---|---|
| 遊びの中核 | 画面全体を覆う透過オーバーレイが戦場になる。敵は**利用者が開いているウィンドウの裏や端から湧き**、キャラが画面手前で技を撃つ。利用者はクリックで狙いを指示し、クールダウンを管理する。1戦3〜5分 |
| 操作 | クリックとホットキー |
| 使う既存機能 | 透過ウィンドウ、常に手前、ホットキー、表情・ポーズ、画面情報（ウィンドウ位置） |
| 新規実装 | 全画面オーバーレイ、当たり判定と敵の挙動、エフェクト描画、入力の受け流し（戦闘外はクリックを下のアプリへ通す） |

## 1-C. LLMを遊びの武器にする

ここまでの案はLLMを**危険物として遠ざけて**いました。これも間違いです。PicoAgentが他の二次創作ゲームに対して持っている最大の差は、**実際に動くAIエージェントを内蔵していること**であり、それを使わない企画を出すなら、そもそもこの製品で応募する意味が薄くなります。

問題は「LLMを使うか否か」ではなく、**LLMの出力のうち、どれがタレントの発言として画面に出るか**です。ここを層で分ければ、利点はほぼ全部取れます。

### LLMでしか作れないもの（6つ）

| 利点 | 具体的に何ができるか | これが無いとどうなるか |
|---|---|---|
| **1. 自由入力を理解する** | 利用者が何を書いても、意図を汲んで話が進む | 選択肢とクリックだけの遊びになる（案1〜13がこれ） |
| **2. 中身が毎回変わる** | 事件、お題、コメント、問題が生成され、二度と同じ回にならない | 内容が尽きた時点で寿命が終わる |
| **3. 利用者の文脈を材料にできる** | その人の作業、過去の会話、好みから、**その人だけの内容**が出る | 誰が遊んでも同じ既製品になる |
| **4. 本当に実行できる** | 検索し、資料を読み、画像を見て、結果を持ち帰る（70種超のスキル） | ゲーム内の「調べる」が演出だけの嘘になる |
| **5. 自由回答を採点できる** | 大喜利、説得、作文、推理の筋道を評価して点を付ける | 正解が1つの問題しか出せない |
| **6. 何をしても反応が返る** | 想定外の入力でも黙らない | 「それはできません」が並ぶ |

### 安全に取り切るための3層

| 層 | LLMの出力 | 画面に出る形 | 監修の対象 |
|---|---|---|---|
| **判定層** | 点数、正否、感情の段階、選択肢ID、次の状態（**構造化データだけ**） | 監修済みテンプレートへ数値を流し込む | **テンプレート一覧だけ**。生成文は表に出ない |
| **モブ層** | 自由な文章 | **視聴者コメント、事件の資料、ナレーション、NPCの発言** | 禁止語と話題のガード。**タレントの発言ではないので、自由に喋らせてよい** |
| **本人層** | 原則として使わない（許諾後に人格ロック＋話題ガードを条件に開く） | キャラの台詞は脚本とテンプレートから出す | 脚本と台詞プール |

**この分け方の要点は、モブ層です。** 「視聴者のコメント」「資料に書かれた文章」「地の文」は**タレントの発言ではない**ので、LLMが自由に書いても、想定外の発言がタレント名義で切り抜かれる事故になりません。上の利点1〜6のうち、2・3・6はモブ層だけでほぼ取れます。案2（配信ごっこ）のコメント欄は、まさにこの層で成立します。

### 審査ビルドはローカルLLMで動かす

**審査する側がAPI鍵を持っている前提に立てません。** 同梱のローカルエンジンで完結させ、鍵の入力なしに起動してすぐ遊べる状態にします。ローカルモデルは応答が短く遅いので、**判定層（短い構造化出力）中心の設計は、性能面でも正しい選択**になります。モブ層の長文生成は、生成が遅れても遊びが止まらない場所（コメント欄の流れ、資料の追加）へ置きます。

### 各案でどこにLLMが効くか

| 案 | 効く層 | LLMが無い場合との差 |
|---|---|---|
| 2. 配信ごっこ | **モブ層**（視聴者コメント） | コメントが定型の使い回しになり、枠を回す面白さが消える |
| 15. 実時間で進む物語 | 判定層（選択の解釈）＋モブ層（地の文） | 脚本のみでも成立するが、自由入力の会話が挟めない |
| 17. 推しに調べさせる推理 | **全層**（指示の解釈・事件生成・資料） | **成立しない。** この案はLLMそのものが遊びの中身 |
| 19. 大喜利（新） | **判定層**（採点と講評） | **成立しない** |
| 20. 説得ゲーム（新） | **判定層**（説得力の評価） | **成立しない** |

### 案19. 大喜利

| | |
|---|---|
| 遊びの中核 | キャラがお題を出す。利用者は自由に回答する。**LLMが面白さを採点**し、点数と一言講評が返る。段位、お題の日替わり、過去の名回答アルバム |
| 操作 | 自由入力 |
| 使う既存機能 | ローカルLLM、既存の入力欄と履歴、表情・ポーズ |

| 強み | **LLMが無ければ1行も成立しない遊び**で、「AIを積んだ製品だから作れる」ことが最短で伝わる。実装は軽い。配信文化と地続きで、ファンが遊ぶ絵が想像しやすい。**採点結果は数値なので、キャラの反応は全部テンプレートで制御できる** |

| 概算 | 小（4〜7人日） |

### 案20. 説得ゲーム

| | |
|---|---|
| 遊びの中核 | 目的が与えられる（企画を通す、締切を延ばしてもらう、機嫌を直してもらう）。利用者は自由に説得し、**LLMが説得力を評価**して態度メーターが動く。規定ターン以内に目標値へ届けば成功 |

## 3. 推奨する提出形（第1次）

**背骨は案15（実時間で進む物語）、目玉は案17（推しに調べさせる推理）**です。小品（案11・案13・案7）は入口として残しますが、主役ではありません。

| 役割 | 何を示すか | 採る案 | LLMの効き方 |
|---|---|---|---|
| **入口** | 起動して30秒で「AIを積んだゲーム」だと分かる | **案19（大喜利）** | 判定層。**無ければ成立しない** |
| **背骨** | 続きが気になる。毎日起動する理由 | **案15** 第1章まで | 判定層＋モブ層（地の文） |
| **目玉** | このアプリでしか作れない遊び | **案17** 事件1本を通しで | 全層。**遊びの中身そのもの** |
| **添え** | 手応えの違う遊びを混ぜる | 案20（説得）、案11、案13 | 案20は判定層、他は無し |
| **将来像** | 企画書で見せる次の絵 | 案2（配信ごっこ）、案14（ボス戦）、案16（謎解き） | 案2はモブ層が主役 |

**応募ビルドは「概ね遊べる」状態で足ります。** 全部を完成させる必要はないので、案19を最初に通し（実装が軽く、AIを積んだ製品であることが一番早く伝わる）、案15の第1章と案17の事件1本が通しで遊べる形を作り、案14は企画書の中の将来像に留めます。案14は絵の派手さが全案で最強なので**予算と時間が許すなら1戦だけでも実物を入れる**価値がありますが、これを主軸に据えると応募までに何も完成しない危険があります。

この構成にした理由は3つです。

- **審査で問われるのは「ファンにとって面白いか」で、「安全か」ではない。** 安全性は前提条件であって、加点項目ではありません。案1〜13は前提条件を満たすだけの作りになっていました。
- **案15は監修と最も相性が良い。** 脚本を渡して読んでもらう形は、二次創作ゲームの監修として最も普通の手順です。台詞の総量は増えますが、**監修の難易度は下がります**。
- **案17は「なぜPicoAgentなのか」への唯一の完全な答え。** 実際に検索し、資料を読み、画像を見るエージェントを持っているのはこの製品だけで、それがそのまま捜査の道具になります。他社が同じ企画を思いついても実装できません。
- **案19を入口へ置いたのは、LLMの利点が最短で伝わるからです。** 自由に書いた回答が採点されて講評が返る体験は、選択肢のゲームでは絶対に作れません。実装は軽く（4〜7人日）、キャラの反応は点数に対応したテンプレートなので**監修対象はテンプレート一覧だけ**で済みます。

企画書では次の順で説明します。

1. **AIを積んでいるから作れる遊び**が、起動してすぐ触れる（案19・案20）。
2. 推しが**実時間で隣にいて、話が進んでいく**（案15）。
3. その中で、**推しに指示を出して本当に調べさせ、推理する**（案17）。
4. これらは**同梱のローカルAIで動く**ので、鍵の登録も通信も要らずに遊べる。
5. 次の段階として、配信ごっこ（案2）と**画面全体を使った戦闘**（案14）を置く。

## 4. どの案でも守る共通設計

- **LLMの出力を3層に分け、キャラの台詞だけを脚本・テンプレートに固定する**（§1-C）。判定層は構造化データだけを返し、文面はテンプレートへ流し込みます。モブ層（視聴者コメント、資料、地の文）はLLMが自由に書いてよく、禁止語と話題のガードで守ります。**本人層は許諾後に人格ロックと話題ガードを条件として開きます。**
- **人格ロック、話題ガード、AI生成である旨の常時表示とセットで出す。** 3件とも未実装です（[IP-LICENSING-STRATEGY.md](IP-LICENSING-STRATEGY.md) §7）。ゲームだけ先に作っても監修の前提を満たしません。
- **音声なしで成立させる。** 効果音やBGMを足す場合は、第三者素材の利用条件を先に揃えます（[docs/TASKS.md](TASKS.md) の販売ゲート「第三者資産」と同じ扱い）。
- **作業を妨げない。** 全画面アプリの実行中は開始しない、頻度を選べる、常にオフにできる、進行は中断しても保存される。
- **課金とランダム要素を結び付けない。** 解放物の抽選を入れる場合も無償の範囲に閉じます（§5）。
- **配布境界を守る。** 実装は`ui/`配下と既存のCSP・`bundle_scope`の許可範囲で行い、外部CDNと`eval`に依存しません。保存は既存の設定・データ領域の作法に従い、審査版の専用領域（`com.picoagent.holo-indie-review`）を通常版と混ぜません。
- **MMDの表現範囲に収める。** 現行のMMD描画はボーン姿勢・表情モーフ・まばたき・音量連動の口モーフまでで、**VMDモーション再生と剛体物理は対象外**です（[SPEC.md](../SPEC.md#mmdキャラクター)）。勝利演出などはポーズと表情の切替、構図の寄りで作ります。
