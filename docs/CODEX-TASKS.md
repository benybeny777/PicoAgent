## P0-4. 停止ボタンを生成中・ツール実行中にも効かせる

- **なぜ**: `pet_cancel`（`commands.rs:3576`）が立てる `AppState::cancel_requested` を `agent::run` が見るのは
  ステップ境界（`agent.rs:1548`）とツール実行直前（`agent.rs:1595`）の2箇所だけ。`chat_with_retry`（`agent.rs:1295`）は
  `cancel` を引数に取らずストリーム受信を最後まで回し、並列ツール実行の `join_all`（`agent.rs:1630`）にも中断点がない。
  そのため長い生成や分単位のツール（`whisper_transcribe` / `meeting_recorder` / `research_report` / `run_command`）の最中は、
  押しても `renderer.js:292` の「停止を要求しています…」のまま待たされる。**公開済み `v1.0.2` に入っている利用者向けの不具合**。
- **やること**:
  1. 中断の伝達を `&AtomicBool` から `tokio::sync::watch::Receiver<bool>`（または `CancellationToken` 相当）へ替える。
     `AtomicBool` のままだと待ち受けができず、ポーリング間隔ぶんの遅れが残る。`commands.rs:124` の `cancel_requested` と
     `pet_cancel` が送信側、`agent::run` の引数が受信側になる。スケジューラ等の `None` 経路は「発火しない受信側」で置き換える。
  2. ストリーム受信ループ（プロバイダ側の `bytes_stream()` を読む箇所）を `tokio::select!` で包み、中断で読み取りを止める。
     **`text::Utf8Stream` の途中で止めるので、確定済みテキストだけを `last` に残すこと**（末尾の未確定バイトを混ぜない）。
  3. `join_all` の各ツール future を `tokio::select!` で包む。中断で抜けた分は、既に `agent.rs:1596`〜にある
     「未実行の tool メッセージを対で積む」処理と同じ形で `tool_call_id` を対応させて履歴へ積む
     （対応が崩れるとプロバイダ側が次の chat を拒否する）。
  4. 子プロセスを持つツールは `process::command()` が `kill_on_drop` を付けているので future の drop で停止するが、
     Windows は孫が残る。2026-08-18 に入れた `taskkill /T /F` の経路を通ること（`tools/process.rs`）を確認する。
- **完了条件**: 遅いダミーツール（10秒以上）と長い生成それぞれで、停止要求から**2秒以内**に `CANCEL_MESSAGE` が返る回帰テストが通ること。
  中断後に同じ会話を継続しても、プロバイダが `tool_calls` の対応崩れでエラーを返さないこと。Windows実機で中断後に子プロセスが残らないこと。
- **触ってはいけない**: 中断時の履歴整合（tool_calls とツール結果の対応）を崩さない。中断を「空応答で成功」にして
  会話へ積まない（サイレントスキップ禁止のルールに触れる）。

## P1-8. `rss_feed` のSSRF検査漏れを塞ぎ、URL引数を取るスキルへガードを付ける

- **なぜ**: `skills/rss_feed/mod.rs:51`〜`80` は**モデルが指定した `url` をそのまま取得している**。
  同じ「外部URLを取りに行く」スキルでも `web_fetch`（`skills/web_fetch/mod.rs:88`）と
  `browser_control`（`skills/browser_control/mod.rs:144` / `291`）は `tools::http::public_http_addresses()` /
  `require_public_http_url()` を通しており、`rss_feed` だけ素通り。既定URL（`PICOAGENT_RSS_DEFAULT_URL`）は空なので、
  実際の入口は引数だけ。モデルはWeb取得結果やRSS本文の影響を受ける（間接プロンプトインジェクション）ため、
  `http://127.0.0.1:<ローカルAPIのport>/` や `http://169.254.169.254/` を読ませられる。`tools::http` がSSRF検査を
  持っているのに一部のスキルだけ通っていない状態は、パスの `permissions::resolve` 漏れと同じ型の抜け。
- **やること**:
  1. `rss_feed` を `web_fetch` と同じ形（`public_http_addresses()` で検査 → 返ったアドレスへ固定して接続）にする。
     アドレス固定まで含めないと、検査後の再名前解決で私設IPへ差し替わる DNS rebinding が残る。
  2. `http_api`（`skills/http_api/mod.rs:18`〜`30`）の許可判定はホスト名一致だけで、
     **許可ドメインが私設IPへ解決される場合は素通り**する。同じアドレス固定を通す。
     利用者が明示した allowlist が前提なので危険度は下がるが、判定を2種類残さない。
  3. `permissions::guard` と同型の設計ガードを `tools::http` へ足す。`guard_scan::skill_sources()` を使い、
     引数から URL を受け取って取得しているのに検査を通していないスキルを検出する。
     **ガードを足さずに `rss_feed` だけ直すのは不可**（同じ抜けが次のスキルで再発する。過去にパス許可判定で7スキル同時に起きている）。
- **完了条件**: `rss_feed` / `http_api` が `127.0.0.1`・`169.254.169.254`・`10.0.0.0/8` 宛のURLを拒否する回帰テストが通ること。
  新設ガードが、検査を外した状態の `rss_feed` を実際に検出して失敗すること（ガード自体が効くことの確認まで）。
- **触ってはいけない**: 正常なRSS取得（公開ホスト）を壊さない。`PICOAGENT_RSS_TIMEOUT_SECS` の意味と既定値は変えない。

## P1-9. 共有HTTPクライアントの「ルールと実装のズレ」を解消する

- **なぜ**: `tools/http.rs:20` は「標準クライアントで接続プールを共有し、個別の待ち時間は `RequestBuilder::timeout` で指定する」
  設計で、`tools::http::guard`（`tools/http.rs:241`）も「共有外の既定クライアントを増やさない」と言っている。
  ところが**実際には54箇所が `reqwest::Client::builder()` で自前クライアントを作っている**
  （スキル35・`src-tauri/src` 19。`providers/*` `aivis.rs` `engine.rs` `components.rs` `commands.rs` を含む）。
  ガードが禁止しているのは `Client::new()` と `reqwest::get(` の2つだけで、`Client::builder()` は素通りするため、
  **ルール文どおりに書いている箇所のほうが少数派**という状態になっている。
  なお待ち時間の穴は無い（54箇所すべてが `.timeout()` か `connect_timeout` を設定済みであることを実測）。
  実害は、呼び出しごとにTLS設定込みのクライアントを作り直すコストと、接続プールが共有されないことの2点。
- **やること**: **まず方針を決めてから**手を動かす。
  - 案A: `client()` + `RequestBuilder::timeout()` へ統一し、ガードの禁止語へ `Client::builder()` を足す。
    一括置換にはせず、触る回にそのファイルだけ移す（54箇所を一度に動かすと回帰の切り分けができない）。
    移行中はガードに理由付き allowlist を置き、残数が見えるようにする。
  - 案B: 自前builderを正式な書き方として認め、`tools/http.rs` の設計コメントとガードの説明文を実態へ合わせる。
    その場合は「自前builderには必ず `.timeout()` を付ける」を明文化し、ガードでそれを検出する
    （現状は54箇所すべてが付けているが、規則として書かれていないので次に足す1箇所で抜ける）。
  - **どちらを採るにせよ、ルール文とガードと実装の3つを一致させて終わること。** 現状の「文書だけが正しい」状態を残さない。
- **完了条件**: 選んだ案が `AGENTS.md`（コネクタ開発ルール）・`tools/http.rs` の設計コメント・ガードの3箇所で一致すること。
  案Aなら移行済み件数と残数がガードの allowlist から数えられること。

## P1-10. スキル提示の「登録順（リンク順）依存」を断つ

- **なぜ**: `tools::all()`（`tools/mod.rs:667`）は `inventory::iter` の順、すなわち**リンク順**でスキルを返す。
  `schemas_for_text()`（同 `752`〜`769`）はその順に走査して `MAX_SELECTED_SCHEMAS = 12` 件で `break` するため、
  **発話に一致したスキルが13件目以降なら黙って落ちる**。落ちるかどうかを決めているのが
  「キーワードの一致度」でも「優先度」でもなく `build.rs` が並べたディレクトリ順・リンク順なので、
  新しいスキルを1つ足す・ツールチェーンを上げる・LTO設定が変わるだけで、**コードを変えていない発話の挙動が変わりうる**。
  既定の同梱ローカルモデル（ctx 8192）は提示ツールの取捨で応答品質が目に見えて変わるため、再現しづらい品質ドリフトになる。
  既存テスト（`通常発話では基本ツールだけを中心に返す` ほか）は特定スキルの有無しか見ておらず、この順序依存を検出できない。
  併せて `capability_summary()`（同 `680`〜`687`）は未ソートの `labels` へ `dedup()` を掛けており、
  `dedup()` は**隣接した重複しか消さない**ため非隣接の重複ラベルを取り逃す。
  スキル名の一意はテストされているが（同 `926`〜）**ラベルの一意はテストされていない**。
  現時点で重複ラベルは0件なので実害は出ていないが、`dedup()` が意図どおり効かない状態で置かれている。
  この列挙は system プロンプトへ入るので、順序がリンク順で揺れることも合わせて直したい。
- **やること**:
  1. `all()` を決定的な順序にする（`name()` 昇順が単純で、テストからも読みやすい）。
     または `schemas_for_text()` / `capability_summary()` 側でソートしてから使う。
     **どちらにせよ「リンク順のまま使う箇所」を残さないこと。**
  2. 12件の打ち切りを「一致度・優先度の高い順に残す」へ変える。P1-5 で `Tool` へ意図判定を移すなら、
     **そこで優先度を一緒に持たせるのが自然**（P1-5 の前か同時にやると二度手間にならない）。
  3. `capability_summary()` は `sort` してから `dedup()` する。ラベルの一意を `全スキルのメタデータとschemaは一意で妥当` へ追加する。
  4. 一致が12件を超える発話（例: 天気・ニュース・為替を1文で聞く）で、**どのスキルが残るかを固定する回帰テスト**を足す。
- **完了条件**: 上記の回帰テストが通ること。`all()` の順序を意図的に入れ替えても `schemas_for_text()` の結果が変わらないこと。
  `capability_summary()` の出力順がビルドによらず一定であること。
- **順序**: P1-5 と同じ関数を触るので、**P1-5 に取り込むか、P1-5 の直前に単独で入れる**。P1-5 の後に回すと、
  移したばかりの意図判定をもう一度書き換えることになる。

## P1-12. キャラ画像をWebP化する（実測 lossless で -45%、q92 で -87%）

## P1-14. CSP から `'unsafe-eval'` を外せるか確かめて外す

- **なぜ**: `src-tauri/tauri.conf.json:31` の CSP は `script-src 'self' 'unsafe-eval' 'wasm-unsafe-eval'` で、
  JavaScript の `eval()` / `new Function()` を許可している。ところが**リポジトリ内に使用箇所が1つも無い**:
  `ui/*.js` で0件、同梱ベンダの `ui/vendor/moveable/moveable.min.js` でも0件（本セッションで実測）。
  WASM のコンパイルは別ディレクティブ `'wasm-unsafe-eval'` が担うので、Live2D Cubism Core が WASM を使うことは
  `'unsafe-eval'` を残す理由にならない。
  このアプリは**モデルが生成した文字列を画面へ出す**（`renderMarkdown` は `createElement` と `textContent` で
  組み立てており `innerHTML` を使っていないので現状は安全）。`'unsafe-eval'` は、将来そこに1箇所でも
  文字列→コード実行の経路が生まれたときに被害を跳ね上げる設定なので、要らないなら外しておきたい。
- **やること**:
  1. `cargo xtask setup live2d` で `ui/vendor/live2d/` を取得し、**Live2D ランタイム本体に `eval(` / `new Function` が
     無いことを確認する**（本セッションの環境では Live2D が Git 管理外で未取得のため、ここだけ確認できていない）。
  2. 無ければ `'unsafe-eval'` を CSP から削り、Live2D キャラ（`hiyori`）の表示・モーション・
     PNG キャラの通常表示・設定画面をひととおり動かす。
  3. 必要だった場合は**外さずに**、`tauri.conf.json` の CSP 行へ「Live2D ランタイムが要求するため残す」と
     理由コメントを残せる形（`SPEC.md` の該当節）へ書く。**理由が分からないまま残っている状態をなくすのが目的**で、
     外すこと自体が目的ではない。
- **完了条件**: `'unsafe-eval'` が消えて全キャラ・全表示形式が動くこと。または、必要な根拠が文書に残ること。
  どちらの結果でも `SPEC.md` のセキュリティ節へ現在のCSPと各ディレクティブの理由を書く。
- **触ってはいけない**: `'wasm-unsafe-eval'`（Live2D の WASM に要る）、`style-src 'unsafe-inline'`（別件。
  外すと既存のインラインスタイルが全部落ちるので、この作業に混ぜない）、`img-src` の `data:` / `asset:`
  （キャラ画像とスクリーンショット添付が通らなくなる）。

## P1-15. cron の「日」と「曜日」の組み合わせが本物のcronと逆の意味になっている

- **なぜ**: `matches_cron()`（`scheduler.rs:550`〜`560`）は5フィールドすべてを **AND** で結んでいる。
  ところが**本物のcronは、「日」と「曜日」の両方が `*` 以外のとき OR で評価する**（`0 9 1 * 1` は
  「毎月1日 **または** 毎週月曜の9時」）。現在の実装では「1日 **かつ** 月曜」になるため、
  年に1回程度しか発火しない。利用者が期待した回数より**黙って少なく**動く。
  `task_scheduler` は**エージェント経由でも登録される**スキルで、モデルは標準cronの意味で文字列を作るため、
  この差は日常的に踏まれる。`validate_cron()` は書式（`1-5` 不可など）は丁寧に断るのに、
  この意味の違いは検査も文書化もされていない（`SPEC.md:759` はフィールドと使える字句の説明だけ）。
  同ファイルのコメントが言うとおり「**無言で動かないのは、エラーで断られるより悪い**」に該当する。
- **やること**: どちらかへ寄せる。**推奨は案A**。
  - 案A: 本物のcronに合わせる。「日」と「曜日」がともに `*` 以外なら OR、片方が `*` なら他方だけを見る。
    モデルと利用者の期待に一致し、驚きが減る。
  - 案B: 両方指定を `validate_cron()` で**断る**（「日と曜日は同時に指定できません。どちらかを `*` にしてください」）。
    実装は軽いが、標準cronで書ける組み合わせが書けなくなる。
  どちらでも `SPEC.md:759` の該当節へ**採用した意味論を明記する**（現在は何も書かれていないのが一番の問題）。
- **完了条件**: `0 9 1 * 1` / `0 9 1 * *` / `0 9 * * 1` の3パターンで、
  「1日かつ月曜」「1日だけ」「月曜だけ」がそれぞれ期待どおりになる回帰テストが通ること。
  既に登録済みのタスク（両方指定のもの）が、更新後に**発火回数が増える**ことを利用者が把握できるよう、
  案Aなら `CHANGELOG.md` へ挙動変更として書く。
- **触ってはいけない**: `1-5` のような範囲指定に対応させない方針（`validate_cron` が明示的に断っている）は変えない。
  この作業は「日と曜日の結合規則」だけに限る。

## P1-16. スリープ・高負荷で分をまたいだ予約が黙って消える

- **なぜ**: `take_due_tasks()`（`scheduler.rs:578`〜）は `Local::now()` の**その分だけ**を照合し、
  常駐ループは30秒間隔（同 `661`）。つまり **PCがスリープしていた・OSが重かった・アプリが起動していなかった**
  分に当たる予約は、次の tick では「現在分」が変わっているので二度と拾われない。ログにも残らないので、
  利用者からは「予約したのに何も起きなかった」だけが見える。
  同ファイルには「長時間タスクを検出ループで `await` すると当該時間帯の他タスクが恒久的にスキップされる」という
  コメント（同 `573`〜`577`）があり、**取りこぼしを嫌う設計意図は既にある**。その穴の残り半分がここ。
  デスクトップペットは常時起動が前提ではない（ノートPCの蓋を閉じる、夜間スリープ）ので、実際に踏まれやすい。
- **やること**:
  1. 最後に検出した時刻を `app_data_dir` の実行履歴側へ持ち、tick ごとに
     「前回検出時刻 → 現在」の**区間に入る予約**を拾う。
  2. 拾い直す範囲に上限（猶予）を設ける。既定は短め（例: 10分）にし、`PICOAGENT_SCHEDULE_CATCHUP_MINUTES` として
     設定キー化する（`0` で従来どおり＝取りこぼしを拾わない）。**設定キーを足したら README と SPEC に必ず記載する**。
  3. 猶予を超えて流れた予約は**実行せず、その事実を `app.<日付>.log` と `schedule-runs.json` へ
     `skipped` として残す**。黙って消える現状を、見える形へ置き換えるのがこの作業の本体。
  4. 同じ分に複数回拾わない既存の `last_run_minute` による二重実行防止は維持する。
- **完了条件**: 検出時刻を過去へずらした状態で tick を回し、(1) 猶予内の予約が1回だけ実行される、
  (2) 猶予外の予約が実行されず `skipped` として記録される、(3) 同じ予約が二重実行されない、の3つを回帰テストで示すこと。
- **触ってはいけない**: 検出（同期）と実行（単一ワーカー）をキューで分ける現在の構造。
  `scheduler::tests` の設計ガードが検出関数の `async` 化を検出するので、検出側で `await` しない。
